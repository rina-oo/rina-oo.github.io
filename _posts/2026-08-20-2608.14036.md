## 들어가며

어제(8월 19일) HuggingFace Daily Papers에서 130표를 받은 논문입니다. 최근 Claude Code, Codex 같은 에이전트 하니스들이 앞다퉈 `SKILL.md` 형태의 "재사용 가능한 절차 지식"을 도입하고 있는데, 정작 "그게 왜 통하는지"를 제대로 뜯어본 연구는 드물었습니다. 대부분의 평가는 "skill을 주니까 벤치마크 점수가 올랐다"는 집계 수치에서 멈춥니다. 이 논문(Princeton, Stanford, UCSD, USC, Johns Hopkins 공동 저자)은 그 한 단계 뒤로 들어가서, 같은 태스크를 raw 실행·workflow memory·skill 세 조건으로 나란히 돌려놓고 "정확히 뭐가 달라지는지"를 8,135개 trial과 528개 쌍대 비교로 파헤칩니다. 제목의 "Why They Work—Until They Don't"라는 표현부터, skill을 무조건 옹호하지 않겠다는 태도가 느껴져서 골랐습니다.

## 한눈에 보기

- **핵심 기여**: (1) raw / workflow memory / skill 세 조건을 동일 trajectory pool에서 통제 비교하는 실험 설계 (2) 8,135개 trial을 정규화하고 240개 trajectory를 open-coding해 12개 skill-use mode(3개 상위 카테고리)로 이루어진 taxonomy를 구축, 사람 검증으로 신뢰도 확보 (Cohen's $\kappa=0.952$) (3) skill retrieval pool을 5→100으로 키우며 "찾을 수 있는가"와 "실제로 도움이 되는가"를 분리해서 측정
- **성능**: skill이 workflow memory 대비 +6.06pp (95% CI [+0.76, +11.36]) 유의미하게 앞섬. Skill의 mechanism 중 65.7%가 procedural anchoring(절차 안정화), 4.5%만이 explicit knowledge injection(사실 주입). Retrieval pool 100개에서 실사용(actual-use) precision이 3.3%까지 붕괴하지만 다운스트림 성공률은 36.4%→39.3%로 오히려 안정적
- **한 줄 요약**: skill은 "몰랐던 사실을 알려주는" 게 아니라 "이미 할 줄 아는 걸 흔들리지 않게 붙잡아주는" 장치이며, 그래서 검색이 완벽하지 않아도 잘 작동하지만 대신 "적용을 잘못하는" 새로운 실패 유형을 만들어낸다

## 어떤 문제를 풀려고 했나

Skill(재사용 가능한 절차 패키지)은 에이전트가 매번 같은 실수를 반복하지 않게, 이전에 발견한 셋업 순서·디버깅 루틴·검증 절차를 압축해서 다시 꺼내 쓰게 하자는 아이디어입니다. Anthropic의 Agent Skills가 대표적이고, 그 외에도 workflow memory, trajectory distillation 등 비슷한 시도가 많습니다.

문제는 지금까지의 평가 방식입니다. "skill을 켜니 성공률이 올랐다"까지는 다들 보여주는데, 그 성공률 상승이 정확히 어디서 오는지는 블랙박스로 남아있었습니다. 저자들은 이걸 세 개의 구체적 질문으로 쪼갭니다.

1. **표현의 문제(RQ1)**: 똑같은 과거 경험이라도 "정리된 workflow memory"로 주는 것과 "표준화된 skill"로 증류해서 주는 것 중 뭐가 더 나은가? 원본 소스는 완전히 동일하게 통제합니다.
2. **신호의 문제(RQ2)**: skill이 도움 되는 게 절차 내용 자체 때문인가, 아니면 "이건 성공했고 이건 실패했다"는 outcome label 덕분인가?
3. **전이의 문제(RQ3)**: 한 에이전트 프레임워크(Codex)에서 만든 skill을 다른 프레임워크(Gemini CLI)로 옮겨도 여전히 통하는가?
4. **검색의 문제(RQ4)**: skill pool이 5개에서 100개로 커지면 정확한 skill을 찾아내는 게 얼마나 어려워지고, 그게 실제 성공률에는 어떤 영향을 미치는가?

이 네 질문을 관통하는 방법론이 논문의 진짜 기여인 **contrastive trajectory analysis**입니다 — 같은 태스크를 raw/workflow/skill 세 arm으로 동시에 실행하고, 세 실행이 정확히 어디서 갈라지는지 LLM judge로 라벨링한 뒤 사람이 검증하는 방식입니다.

## 핵심 아이디어

### 실험 파이프라인: 같은 trajectory, 다른 표현

다음은 논문의 핵심 실험 설계를 보여주는 그림입니다.

![실험 파이프라인](/assets/img/posts/2608.14036/fig1_pipeline.png)
_Docker 컨테이너에서 원본 trajectory를 수집하고, 성공/실패 비율을 5s0f~0s5f로 조절한 뒤 같은 pool을 workflow memory와 SKILL.md로 각각 증류해서 통제 비교한다_

왼쪽부터 보면, 에이전트에게 Docker 컨테이너·태스크 지시문·(있다면) 주입된 skill이 주어지고, 실행 후 테스트로 검증합니다. 여기서 나온 trajectory 중 성공(파란 원)과 실패(주황 원)를 특정 비율로 섞은 "Trace Combinations" — 5개 성공 0개 실패(5s0f)부터 0개 성공 5개 실패(0s5f)까지 6단계 조합 — 을 만듭니다. 이 조합이 핵심 통제 변수입니다. 같은 조합을 그대로 두 갈래로 증류합니다: 하나는 원래 실행 흐름을 최대한 보존하는 Workflow Memory, 다른 하나는 `skill-creator.md` 프롬프트를 통해 "반복 가능한 절차, 순서, 실패 모드, 검증 방법"만 뽑아낸 `SKILL.md`입니다. 이렇게 하면 "더 많은 경험을 줬다"가 아니라 "같은 경험을 어떻게 포장했다"만 바뀐 순수한 비교가 됩니다.

### 핵심 발견: 절차 앵커링 vs 사실 주입

저자들이 가장 강조하는 수치는 성공률 자체가 아니라, **skill이 왜 성공률을 올리는가**입니다. 528개 쌍대 비교에서 성공률만 보면 이렇습니다.

$$\text{Raw: } 312/528 = 59.1\% \quad \text{Workflow: } 295/528 = 55.9\% \quad \text{Skill: } 327/528 = 61.9\%$$

여기서 $59.1\%$, $55.9\%$, $61.9\%$는 각 조건(arm)에서 528개의 매칭된 태스크 중 성공한 비율입니다. 흥미로운 건 skill이 raw보다 나은 정도(+2.8pp, CI에 0을 포함해 통계적으로 불확실)보다 skill이 workflow memory보다 나은 정도(+6.06pp, CI [+0.76, +11.36]로 확실히 양수)가 더 크고 견고하다는 점입니다. 같은 원본 재료에서 나왔는데 표현 방식만 바꿨을 뿐인데 이 차이가 난다는 게 이 논문의 핵심 주장을 뒷받침합니다.

그럼 skill이 정확히 뭘 하길래 이런 차이가 날까요? 여기서 mechanism label이 등장합니다. LLM judge가 각 trajectory에서 주입된 자료(workflow memory 혹은 skill)가 실제로 어떻게 쓰였는지를 다섯 가지로 분류합니다: `procedural_anchor`(사용 가능한 절차·순서·체크리스트 제공), `knowledge_injection`(몰랐던 사실 제공), `failure_warning`(함정 경고), `none`(의미 없이 무시됨), `counterproductive`(오히려 방해).

결과는 명확합니다. skill mechanism 중 **65.7%가 procedural_anchor**이고, `knowledge_injection`은 **4.5%**에 불과합니다. 즉 skill이 에이전트를 도울 때, 그건 "이 API 파라미터는 이렇게 써야 해" 같은 몰랐던 지식을 알려줘서가 아니라 "셋업은 이 순서로, 확인은 이 시점에" 같은 실행 절차를 안정시켜서라는 겁니다. 개인적으로 이 구분이 상당히 직관에 반한다고 느꼈는데, skill을 만들 때 보통 "이 도구는 이렇게 동작한다"는 배경 지식을 정성껏 적어넣게 되는데, 실제로 성공을 견인하는 건 그런 지식보다 "다음에 뭘 해야 하는지"를 흔들리지 않게 고정해주는 역할이라는 뜻이니까요.

### 실패 유형의 지형도: 어디서 이기고 어디서 지는가

다음 그림은 raw/workflow/skill 세 조건에서 12개 mode의 분포가 trajectory mixture(5s0f~0s5f)별로 어떻게 달라지는지 보여줍니다.

![Taxonomy 분포](/assets/img/posts/2608.14036/fig2_taxonomy.png)
_세 패널이 각각 Raw, Workflow Memory, Skill. 초록 계열은 성공(SC1), 파랑 계열은 실행/검증 실패(SC2), 빨강/주황 계열은 호출/한계 실패(SC3)_

가로축은 trajectory mixture(성공/실패 원본을 몇 개씩 섞었는지), 세로축은 88개(528/6) trajectory 중 각 mode에 해당하는 개수입니다. Skill 패널(오른쪽)을 보면 진한 초록(`skill-guided success`)이 압도적으로 크고, 특히 mixture가 실패 쪽으로 기울어져도(0s5f로 갈수록) Raw나 Workflow보다 초록 영역이 상대적으로 잘 유지됩니다. 반면 Workflow 패널(가운데)에서는 빨간 영역(`timeout/budget exhaustion`, SC3)이 눈에 띄게 두껍습니다 — 원본 trajectory를 거의 그대로 보존하다 보니 탐색 과정의 노이즈까지 다 들고 와서 context budget을 잡아먹는다는 뜻입니다.

또 하나 눈여겨볼 부분은 Skill 패널에만 있는 주황색 영역(`skill guidance misapplied`)입니다. Raw와 Workflow에는 이 mode가 거의 없는데(각각 0.8%, 0.4%), Skill에서는 **10.0%**로 뛰어오릅니다. Skill이 만들어내는 고유한 실패 유형이라는 거죠 — skill 자체는 그럴듯한데, 에이전트가 조건을 놓치고 기계적으로 따라하거나 더 이상 맞지 않는 전제를 그대로 가져다 쓰는 경우입니다.

수치로 요약한 표는 아래와 같습니다.

| SC | Mode | Raw | Workflow | Skill |
|---|---|---:|---:|---:|
| SC1 | `skill_guided_success` | 10.4% | 0.4% | **61.6%** |
| SC1 | `workflow_guided_success` | 0.0% | **54.5%** | 0.0% |
| SC1 | `autonomous_clean_success` | **48.7%** | 0.8% | 0.2% |
| SC2 | `environment_infrastructure_failure` | **5.3%** | 1.7% | 0.2% |
| SC2 | `output_format_schema_mismatch` | **7.4%** | 3.8% | 3.2% |
| SC2 | `background_service_lifecycle_failure` | **2.7%** | 2.5% | 0.8% |
| SC2 | `shell_code_corruption` | 1.1% | **1.9%** | 0.2% |
| SC2 | `algorithmic_logic_error` | 8.3% | **11.0%** | 7.4% |
| SC2 | `static_verification_without_runtime` | 12.5% | 12.5% | **11.7%**(거의 동일) |
| SC3 | `timeout_budget_exhaustion` | 1.7% | **10.6%** | 4.4% |
| SC3 | `skill_guidance_misapplied_or_ignored` | 0.8% | 0.4% | **10.0%** |
| SC3 | `capability_or_safety_limit` | **1.1%** | 0.0% | 0.4% |

패턴을 짚어보면, SC2(실행/검증 실패) 계열은 skill이 대체로 raw보다 낮습니다 — 특히 `environment_infrastructure_failure`가 5.3%→0.2%로 급감하는데, 이건 "환경 셋업 문제"가 절차로 완전히 해결 가능한 영역이라는 뜻입니다. 반면 `algorithmic_logic_error`(알고리즘 자체가 틀림)와 `static_verification_without_runtime`(런타임 검증 없이 정적으로만 확인하고 넘어감)는 세 조건 모두에서 비슷한 수준으로 남아있습니다. 즉 skill은 "실행을 안정시키는 문제"는 잘 풀지만 "애초에 틀린 논리를 고쳐주는 문제"는 손대지 못한다는 경계가 명확히 보입니다.

### 실제 trajectory로 확인하는 차이

부록에 있는 `react-performance-debugging` 태스크의 실제 세 trajectory 비교가 이 차이를 아주 구체적으로 보여줍니다. Raw 실행은 아예 엉뚱한 곳(hydration 문제)을 붙잡고 씨름하다 외부 API 호출 검증에서 실패합니다. Workflow Memory는 문제(server-side waterfall)는 제대로 짚었지만, 프로필 요청을 여전히 순차적으로 처리해서 지연시간 테스트(800ms 이내)에서 915ms로 실패합니다. Skill은 주입된 `SKILL.md`가 "독립적인 await는 Promise.all로, 부분적으로 의존적인 흐름은 선행 조건이 풀리는 즉시 다음 fetch를 트리거하라"는 구체적 패턴을 제시하고, 에이전트가 이를 그대로 적용해 11개 테스트를 모두 통과합니다. 여담이지만 이 예시 하나가 "procedural anchor"라는 추상적 용어보다 훨씬 와닿습니다 — 세 arm이 정확히 같은 버그를 붙잡고 각기 다른 수준으로 고치는 걸 나란히 보여주니까요.

### Outcome label의 역할

RQ2는 skill을 만들 때 "이 trajectory는 성공했다/실패했다"는 라벨을 보여주는 것과 숨기는 것(no-hint)의 차이를 봅니다.

![No-hint 비교](/assets/img/posts/2608.14036/fig5_nohint.png){: style="max-width: 480px;" }
_왼쪽부터 Terminal-Bench-2, SkillsBench, Terminal-Bench-Pro. 위쪽은 Codex, 아래쪽은 Gemini CLI. 파란 막대가 outcome label을 보여준 normal, 주황 막대가 숨긴 no-hint_

여섯 개 패널 모두 가로축은 trajectory mixture(5s0f~0s5f), 세로축은 성공률이고 점선이 raw baseline입니다. 위쪽 세 패널(Codex)에서는 5s0f·4s1f처럼 성공 trajectory가 많을 때는 파란 막대(normal)와 주황 막대(no-hint)가 거의 붙어있는데, 실패 trajectory 비중이 늘어날수록(2s3f, 1s4f, 0s5f 쪽으로 갈수록) 주황 막대가 파란 막대 아래로 눈에 띄게 처집니다 — 특히 TB2의 0s5f에서는 normal이 0.52인데 no-hint는 0.39까지 떨어집니다. 아래쪽 Gemini 패널에서는 이 격차가 훨씬 일찍부터, 거의 모든 mixture에서 두드러집니다. 논문 서술에 따르면 Gemini + Terminal-Bench-2의 3s2f 조합은 라벨이 있을 때 0.7462, 없을 때 0.4000으로 거의 두 배 차이가 납니다. 즉 skill이 실패 사례에서 뭔가를 배우려면 "이건 실패였다"는 명시적 신호가 필요하다는 뜻이고, 실패만 있는 raw trace를 무작정 넣는 것만으로는 유용한 skill이 잘 안 나온다는 걸 시사합니다.

### 검색이 별개의 병목이다

skill이 아무리 좋아도 pool에서 찾아내지 못하면 소용없습니다. RQ4는 이걸 세 개의 독립적인 실험(Arm)으로 나눠서 봅니다: Arm 1은 embedding 기반 순수 검색, Arm 2는 태스크 실행 없이 에이전트가 직접 고르는 명시적 선택, Arm 3은 pool 전체를 실행 환경에 두고 실제로 무엇을 썼는지 파싱하는 것입니다. Precision/Recall은 다음과 같이 정의됩니다.

$$P_i = \frac{|\widehat{G}_i \cap G_t|}{|\widehat{G}_i|}, \qquad R_i = \frac{|\widehat{G}_i \cap G_t|}{|G_t|}$$

여기서 $G_t$는 태스크 $t$의 정답 skill 집합(벤치마크가 제공하는 ground truth), $\widehat{G}_i$는 이번 trial에서 실제로 선택되거나 사용된 skill 집합입니다. $P_i$는 "내가 고른 것 중 몇 개가 맞았나", $R_i$는 "정답 중 몇 개를 찾아냈나"를 뜻합니다. 여러 trial에 대해서는 각 $P_i$, $R_i$를 산술 평균 내서 최종 $P$, $R$을 구하고, $F_1$은 평균 낸 뒤의 $P$, $R$로 다시 계산합니다.

다음 그림이 이 세 Arm의 precision을 pool 크기별로 비교합니다.

![Retrieval precision 비교](/assets/img/posts/2608.14036/fig3_retrieval_precision.png){: style="max-width: 480px;" }
_파란 원이 embedding 검색, 주황 사각형이 에이전트의 명시적 선택, 초록 삼각형이 실제 실행 중 파싱된 사용. Pool 크기(가로축, 로그성 간격)가 커질수록 세 곡선이 모두 하락하지만 기울기가 완전히 다르다_

가로축은 skill pool 크기(5, 10, 20, 50, 100), 세로축은 precision(%)입니다. 세 곡선을 세로로 비교해보면, 파란색(embedding 검색)은 88%에서 77%로 완만하게, 주황색(agent selection)은 70%에서 64%로 역시 완만하게 떨어지는 반면, 초록색(실제 실행 중 사용)은 **30%에서 4% 밑으로 급락**합니다. 즉 "오프라인에서 정답을 골라내는 능력"과 "실제 실행 중에 정답만 정확히 사용하는 능력"이 완전히 다른 곡선을 그린다는 겁니다. 논문은 이걸 "exact ground-truth invocation은 성공의 필요조건도 충분조건도 아니다"라고 표현합니다 — pool이 100개로 커져도 recall은 54~74%나 유지되는데(즉 여러 후보를 다 건드려보긴 함), 그중 정답 하나만 정확히 골라 쓰는 precision만 무너진다는 거죠.

더 놀라운 건 그럼에도 다운스트림 성공률은 크게 안 무너진다는 점입니다. Codex+Gemini 두 pairing 평균으로 pool 5→100에서 actual-use precision은 29.6%→3.3%로 붕괴하는데, 다운스트림 성공률은 36.4%→39.3%로 오히려 소폭 상승합니다. 관련은 있지만 정답이 아닌 skill도 부분적으로 도움이 된다는 뜻으로 읽힙니다.

### 프레임워크를 옮겨도 살아남는가

RQ3은 Codex + GPT-5.3-Codex에서 만든 skill/workflow memory를 그대로 Gemini CLI + Gemini-3.1-Pro-Preview에 얹어봅니다.

![Cross-framework 전이](/assets/img/posts/2608.14036/fig4_cross_agent.png)
_점선이 Gemini CLI의 raw baseline(56%). 주황이 Codex에서 만든 workflow memory를 이식, 초록이 같은 방식으로 만든 skill을 이식_

세로축은 성공률, 막대 위 숫자가 실제 값이고 초록 막대 옆 `+N`이 raw 대비 skill의 이득입니다. Workflow memory(주황)는 대부분 raw baseline(56%, 점선) 근처에 머물거나 오히려 아래(0s5f에서 54%)로 떨어지는 반면, skill(초록)은 모든 mixture에서 baseline을 웃돌고 5s0f 조합에서는 84%까지 올라가 +30pp라는 가장 큰 이득을 보입니다. 다른 프레임워크의 실행 트레이스를 통째로 옮기면 그 프레임워크 특유의 프롬프트 스타일이나 도구 호출 방식이 섞여 있어서 오히려 방해가 되지만, skill로 한 번 증류하고 나면 그런 프레임워크 종속성이 상당히 걷힌다는 뜻으로 해석됩니다.

## 아쉬운 점 / 의문점

논문이 스스로 인정하는 한계는 세 가지입니다: 평가가 터미널·도구 사용 벤치마크에 국한되어 장기 웹 상호작용이나 개방형 협업 같은 다른 에이전트 행동 범주는 다루지 못했다는 점, 몇 개 안 되는 agent-model 조합(Codex+GPT-5.3-Codex, Gemini CLI+Gemini-3.1-Pro)만 봤다는 점, 그리고 taxonomy가 전체 8,135개 레코드의 약 3%인 240개 샘플에서 open-coding으로 유도됐다는 점입니다.

리뷰어로서 몇 가지 더 짚고 싶은 점이 있습니다.

첫째, RQ4의 Codex pairing이 GPT-5.4로 바뀐 부분입니다. 저자들은 "GPT-5.3-Codex를 같은 평가 접근으로 더 이상 쓸 수 없어서"라고 밝히고 RQ4 결과를 RQ1-3과 직접 비교하지 말라고 명시했는데, 이건 정직한 태도이긴 하지만 결국 논문 전체를 관통하는 하나의 일관된 모델 세트로 결론을 내리지 못했다는 뜻이기도 합니다. 벤치마크 접근권이 순식간에 사라지는 요즘 LLM 연구 환경의 현실을 보여주는 사례이기도 하고요.

둘째, Claude Code 결과가 각주로만("본 버전에서는 제시하지 않음") 언급되고 실제로는 빠져 있습니다. Skill 개념을 처음 대중화한 게 Anthropic인데 정작 Claude Code 자체 결과가 빠진 건 다소 아쉽습니다. 리소스 제약 때문일 수도 있고, 혹은 Claude Code에서 나온 패턴이 이 논문의 서사와 잘 안 맞았을 가능성도 배제할 수 없는데, 이 부분은 논문에 명시되어 있지 않아 정확히는 모르겠습니다.

셋째, taxonomy 라벨링과 mechanism 분류 자체가 LLM judge에 의존합니다. 저자들이 human validation(95.8% 일치, $\kappa=0.952$)을 진행한 건 좋은 통제지만, 이 검증은 "238개 raw label이 12개 canonical mode 중 어디에 속하는지"를 사람이 재확인한 것이지, "528개 paired triple 전체"를 사람이 직접 라벨링한 게 아닙니다. 논문도 이 점을 한계로 인정하고 있어서 정직하지만, "skill이 65.7%의 경우에 procedural anchor로 작동한다"는 핵심 수치 자체는 여전히 LLM judge의 판단에 크게 의존한다는 점은 염두에 둘 필요가 있습니다.

넷째, 이 논문은 "왜 통하는가"는 아주 잘 보여주지만 "그래서 어떻게 하면 더 나은 skill을 자동으로 만들 수 있는가"는 아직 다음 과제로 남겨둡니다. Conclusion에서도 "이 분석이 향후 skill 자동 생성의 기초가 되길 바란다"고만 말하는데, procedural anchoring이 핵심 메커니즘이라는 걸 알았다면 skill 생성 프롬프트를 그 방향으로 최적화하는 후속 실험을 기대했는데 여기서는 다루지 않습니다.

## 마치며

이 논문의 가장 실용적인 시사점은 개인적으로 "skill을 만들 때 배경 지식을 욱여넣지 말고 절차와 체크리스트에 집중하라"는 것과 "skill retrieval을 완벽하게 맞추려는 노력보다는, 애매하게라도 관련된 skill을 pool에 노출시키는 것 자체가 도움이 될 수 있다"는 것입니다. Retrieval precision 3%짜리 시스템이 성공률을 떨어뜨리지 않는다는 결과는, 검색 정확도에 과도하게 매달리기보다 skill의 콘텐츠 품질 자체에 투자하는 게 더 나은 ROI일 수 있다는 뜻으로 읽힙니다. 다음에 이 팀이 procedural anchoring 메커니즘을 직접 최적화 타깃으로 삼은 skill 자동 생성 연구를 내놓는다면 흥미롭게 지켜볼 것 같습니다.
