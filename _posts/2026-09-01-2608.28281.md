## 들어가며

어제(8월 31일) HF Daily Papers에서 82표를 받은 논문입니다. Alibaba의 DreamX Team이 냈는데, 제목의 "Loop Engineering"이라는 단어부터 지금 이 리뷰를 쓰고 있는 저 자신의 작업 방식과 맞닿아 있어서 눈길이 갔습니다.

요즘 코딩 에이전트를 쓰는 방식이 조금씩 바뀌고 있습니다. 예전에는 사람이 매 턴 프롬프트를 손으로 써서 넣었다면, 이제는 "목표와 검증 기준만 정해두고, 진행 상황을 모니터링하면서 다음에 뭘 시킬지, 언제 멈출지를 결정하는" 루프를 따로 설계하는 방식이 늘고 있습니다. Codex의 `/goal` 기능이나, 이 블로그를 매일 발행하는 스크립트 자체도 사실 작은 규모의 "루프"입니다. 그런데 이런 루프가 실패하면 원인을 알기가 어렵습니다. 코딩 에이전트 자체가 못한 건지, 아니면 루프가 잘못된 진행 상황 보고를 믿었거나, 필요한 검증을 건너뛰었거나, 예산을 엉뚱한 데 썼거나, 안전하지 않은 시점에 멈춰버린 건지 최종 결과물 하나만 봐서는 구분이 안 됩니다. 이 논문은 바로 이 지점 — "코딩을 잘하는 능력"과 "코딩 루프를 잘 관리하는 능력"을 분리해서 후자만 따로 재보자는 시도입니다.

## 한눈에 보기

- **핵심 기여**: 코드를 직접 짜는 Worker는 고정하고, 매 라운드마다 "다음에 뭘 시킬지 혹은 멈출지"만 결정하는 별도의 모델(Controller)을 평가 대상으로 삼는 LoopArena를 제안. Evidence Packet(구조화된 진행 보고서)과 Loop Contract(다음 지시)라는 프로토콜로 Controller와 Worker 사이를 엄격히 분리하고, 실행 비용이 다른 세 단계(Type I: 단일 결정 선택 / Type II: 부분 태스크 / Type III: 전체 태스크)로 5개 모델을 비교
- **성능**: 전체 태스크(Type III)에서 가장 잘하는 Controller(GPT-5.5)조차 Strict Success Rate 24.69%에 그치고, 목표를 그냥 반복해서 되풀이하는 단순 정책(fixed control)은 전체 태스크에서 아예 개입하지 않는 것(no control)과 정확히 같은 18.52%를 기록
- **한 줄 요약**: 코드를 잘 짜는 것과 그 작업을 잘 지휘하는 것은 다른 능력이고, 지금 가장 좋은 모델도 후자에서는 4번 중 1번밖에 성공하지 못합니다.

## 어떤 문제를 풀려고 했나

SWE-bench류의 기존 코딩 벤치마크들은 에이전트를 끝까지 돌려서 최종 저장소 상태를 채점합니다. 문제는 이 방식이 "코딩 능력"과 "루프 관리 능력"을 한 덩어리로 묶어버린다는 점입니다. 저자들은 관련 연구를 세 갈래로 정리하며 이 공백을 짚습니다.

첫째, SWE-bench나 그 변형들은 코딩 에이전트 시스템 전체를 하나의 블랙박스로 채점합니다. 둘째, Harness-Bench나 LoopsBench 같은 최근 연구는 "모델+하네스" 조합 전체를 비교하지만, 여전히 평가 대상은 완성된 시스템 하나입니다. 셋째, 스텝 단위 프로세스 평가(process-reward, critique 벤치마크)는 개별 결정의 품질을 보되, 그 결정이 실제로 실행됐을 때 어떤 결과로 이어지는지는 보통 추적하지 않습니다.

LoopArena가 다르게 접근하는 지점은 "평가 대상 자체를 바꾼다"는 것입니다. 코딩을 실제로 수행하는 Worker와 실행 환경, 도구, 예산, 평가 기준을 전부 고정해버리고, 오직 "이번 라운드가 끝난 뒤 다음에 뭘 시킬지"를 결정하는 모델(Controller)만 갈아 끼우면서 비교합니다. 그러면 결과 차이는 온전히 Controller의 판단력 차이로 귀속됩니다 — 적어도 이론적으로는요.

## 핵심 아이디어

### 1) Controller-Worker-Reporter 삼각 구조

다음은 LoopArena 실행 하네스의 전체 구조를 보여주는 그림입니다.

![LoopArena 하네스 구조](/assets/img/posts/2608.28281/fig1_looparena_harness.png)
_Figure 1. Controller-guided 조건(위)과 No-control 조건(아래)이 같은 출발점에서 갈라져 같은 평가자로 모이는 구조_

위쪽 "CONTROLLER-GUIDED" 블록을 보면, 바깥쪽 주황색 점선(Outer loop)과 안쪽 파란색 점선(Inner loop · ReAct)이 분리되어 있습니다. Worker(파란 박스)는 Observe → Reason → Act → 저장소 편집/도구 사용을 반복하는 일반적인 ReAct 루프를 돕니다. 이 Worker가 할당된 구간 작업을 끝내면, 그 시점의 대화 히스토리 사본을 가지고 임시 Reporter(오른쪽 위, "Temporary session"이라고 점선 표시된 부분)가 소환됩니다. Reporter는 읽기 전용으로만 저장소를 살펴보고 상태를 요약하는데, 이 요약 대화는 저장 되지 않고 버려집니다 — 즉 Reporter가 뭔가 잘못 판단해도 그게 Worker의 진짜 작업 히스토리를 오염시키지 않습니다. 하네스가 이 요약을 Evidence Packet으로 정형화하면, Controller(빨간 박스)가 그걸 읽고 Loop Contract(다음 지시, 혹은 정지 결정)를 냅니다. 이 Contract는 다시 하네스에 의해 Worker의 다음 프롬프트로 렌더링됩니다.

아래쪽 "NO CONTROL" 블록은 이 외부 루프 전체가 아예 없는 조건입니다. 왼쪽에서 같은 "Restored task state"로 시작해서, 오른쪽의 같은 "Shared task evaluator"로 모인다는 점이 이 그림에서 가장 중요한 부분입니다. 시작점과 채점 기준이 완전히 동일하기 때문에, 두 조건의 결과 차이는 정말로 "Controller가 개입했는가 아닌가"에서만 나옵니다.

이 상호작용을 논문은 다음과 같이 정식화합니다. Controller가 각 제어 사이클마다 내리는 결정은 이렇게 씁니다.

$$c_{i,k} = \pi(x_{i,k}, h_{i,k})$$

여기서 $\pi$는 평가 대상 Controller 모델, $x_{i,k}$는 태스크 $i$의 $k$번째 제어 사이클에서 주어지는 Evidence Packet, $h_{i,k}$는 그 이전까지 쌓인 대화 히스토리(과거 Packet들과 Contract들)입니다. 출력 $c_{i,k}$가 Loop Contract입니다.

이 식에서 눈여겨볼 부분은 우변에 없는 것들입니다. Controller는 코드도, 테스트 결과도, 저장소 상태도 직접 보지 못합니다. 오직 Reporter가 걸러낸 요약 $x_{i,k}$와 과거 대화만으로 다음 수를 둬야 합니다. 즉 LoopArena가 재는 건 "코드를 잘 짜는 능력"이 아니라 "요약된 증거만 보고 옳은 다음 지시를 내리는 능력"입니다 — 야구로 치면 직접 타석에 서는 게 아니라 덕아웃에서 사인만 내는 감독의 능력을 재는 셈이죠.

### 2) 실행 비용이 다른 세 단계: Type I / II / III

다음은 하나의 실제 코딩 태스크로부터 세 가지 평가 형태가 어떻게 파생되는지를 보여주는 그림입니다.

![Type I·II·III 구성 방법](/assets/img/posts/2608.28281/fig2_looparena_task_forms.png)
_Figure 2. 같은 저장소와 같은 Controller-guided trajectory로부터 세 가지 실행 형태를 구성하는 방법_

왼쪽의 "FROM REAL CODING TASKS"를 보면 재료는 두 가지입니다 — 실제 저장소 하나, 그리고 그 저장소에서 이미 한 번 Controller가 개입해 실행된 궤적(색색의 점이 찍힌 꺾은선 그래프). 이 두 재료로부터 세 개의 가로 띠가 파생됩니다.

맨 위 **Type I**(주황)은 이 궤적 중 한 시점을 골라, 그 시점의 Evidence Packet과 네 개의 후보 Loop Contract(A~D)를 제시하고 "다음에 어떤 Contract를 내야 하는가"를 묻는 4지선다 문제입니다. 오른쪽에 "Replay validated · No code execution"이라고 적힌 부분이 핵심인데, 정답은 벤치마크를 만들 때 네 후보를 실제로 실행해서 결과를 보고 미리 정해뒀기 때문에, 평가 시점에는 Worker를 전혀 돌리지 않고 텍스트 선택만으로 채점할 수 있습니다.

중간 **Type II**(회색)는 이미 앞부분 작업이 끝난 "준비된 중간 워크스페이스"(module_a.py, module_b.py에 체크 표시)에서 시작해서, 남은 한 단계만 Controller-Worker 루프가 완수하게 시킵니다. "Condensed start · Partial scope"라는 표시처럼 범위가 좁습니다.

맨 아래 **Type III**(파랑)는 같은 저장소를 처음부터(모든 파일이 원 표시, 아직 미완료) 시작해서 전체 태스크를 완주시킵니다. "Original start · Full scope"입니다.

이 그림에서 제가 인상 깊었던 부분은, Type II와 Type III가 정말로 "같은 태스크의 다른 시작점"이라는 걸 시각적으로 못박아둔다는 점입니다. 서로 다른 태스크를 비교하는 게 아니라 똑같은 태스크를 축소판/원본으로 짝지어 비교하기 때문에, 두 세팅 사이의 순위 차이가 있다면 그건 "범위(scope)"라는 단일 변수 때문이라고 해석할 수 있습니다.

### 3) 평가 지표: Strict Success Rate와 비용 절감률

Type II와 Type III의 성공률은 이렇게 집계됩니다.

$$\operatorname{SSR}_{t}(p) = \frac{1}{N_t K}\sum_{i=1}^{N_t}\sum_{r=1}^{K} Y^{(t)}_{p,i,r}$$

$N_t$는 해당 세팅의 태스크 수, $K=3$은 반복 실행 횟수, $Y^{(t)}_{p,i,r} \in \{0,1\}$은 정책 $p$가 태스크 $i$의 $r$번째 반복에서 성공했는지 여부입니다.

식 자체는 단순한 평균 성공률이지만, $K=3$으로 매 태스크를 세 번씩 반복 실행한다는 점이 중요합니다. 뒤에서 다시 보겠지만, 같은 정책이 같은 태스크에서도 실행마다 성공/실패가 갈리는 경우가 적지 않아서, 이 반복이 없으면 순위 자체가 운에 좌우될 위험이 큽니다.

Type II가 Type III의 값싼 대체 지표로 쓸 수 있는지 검증하려고, 저자들은 Controller별 비용 절감률을 이렇게 정의합니다.

$$R_C = \frac{100}{|\Pi|}\sum_{\pi \in \Pi}\left(1 - \frac{\overline{C}_{\mathrm{II}}(\pi)}{\overline{C}_{\mathrm{III}}(\pi)}\right)$$

$\Pi$는 평가 대상 Controller 모델 집합(참조 정책 제외), $\overline{C}_t(\pi)$는 세팅 $t$에서 Controller $\pi$의 평균 추정 추론 비용입니다.

Controller별로 "Type II 비용이 Type III 대비 몇 % 줄었는가"를 구해 평균 낸 값이 64.4%였습니다. 개인적으로는 이 부분이 이 논문에서 가장 실용적인 기여라고 느꼈습니다. 저처럼 API 비용이 부담스러운 개인 연구자 입장에서는, "값싼 대리 지표가 진짜 지표와 얼마나 일치하는가"를 순위상관계수(Spearman's $\rho=0.9747$, 뒤에서 다시 다룹니다)로 정량화해준 게 실제로 벤치마크를 설계할 때 참고할 만한 정보라고 생각합니다.

## 실험 결과

Worker는 세 세팅 모두 Qwen3.7-Plus로 고정했고, Controller로는 Qwen3.7-Plus, DeepSeek-V4-Flash-0731, GLM 5.2, GPT-5.5, Claude Opus 4.8 다섯 모델을 평가했습니다. 주요 결과는 다음과 같습니다.

| Method | Type I<br>Contract Acc.(%) ↑ | Type II<br>SSR(%) ↑ | Type II<br>Est. cost($/run) ↓ | Type III<br>SSR(%) ↑ | Type III<br>Est. cost($/run) ↓ |
|---|---|---|---|---|---|
| *참조 정책* | | | | | |
| No control | — | 39.51 | 1.04 | 18.52 | 2.01 |
| Fixed control | — | 46.91 | 1.08 | 18.52 | 5.58 |
| *Controller 모델* | | | | | |
| Qwen3.7-Plus | 72.22 | _48.15_ | 4.30 | _23.46_ | _6.89_ |
| DeepSeek-V4-Flash-0731 | _77.78_ | 45.68 | _2.10_ | 19.75 | 10.24 |
| GLM 5.2 | 74.44 | 37.04 | **1.63** | 16.05 | **4.86** |
| GPT-5.5 | **87.78** | **51.85** | 5.00 | **24.69** | 18.84 |
| Claude Opus 4.8 | 76.67 | _48.15_ | 5.87 | 20.99 | 16.82 |

(굵게 표시된 값이 1위, 기울임이 2위입니다.)

이 표에서 가장 눈에 띄는 패턴은 숫자 하나하나가 아니라 **Fixed control의 이상한 행동**입니다. Fixed control은 "매 제어 시점마다 원래 목표를 그대로 되풀이해서 지시하는" 아주 단순한 정책인데, Type II(부분 태스크)에서는 No control보다 눈에 띄게 낫습니다(39.51% → 46.91%). 그런데 Type III(전체 태스크)로 가면 정확히 No control과 같은 18.52%로 주저앉습니다. 저자들은 이를 "목표를 반복해서 되새겨주는 것만으로는 짧은 구간에서는 도움이 되지만, 구현·검증·복구·정지를 오가야 하는 긴 태스크에서는 상태에 맞게 적응하는 가이드가 필요하다"는 신호로 해석합니다. 저도 이 해석에 동의하는데, 부분적으로만 남은 일감은 "계속해"라는 말 한마디로도 충분히 이어갈 수 있지만, 처음부터 끝까지의 전체 여정에서는 지금이 구현 단계인지 검증 단계인지 판단하는 게 그 자체로 별개의 능력이라는 뜻이니까요.

두 번째로 중요한 결과는 Type II와 Type III 사이의 순위 일치입니다. Controller 5개 중 9개 쌍이 두 세팅 모두에서 순서가 뒤집히지 않았고(10개 쌍 중 하나는 동점), Spearman's $\rho = 0.9747$이라는 높은 상관을 보입니다. 비용은 평균 64.4% 줄이면서 순위는 거의 그대로 유지된다는 뜻이니, 매번 전체 태스크를 돌리기 부담스러운 상황에서 Type II를 저비용 대리 지표로 쓸 근거가 됩니다.

세 번째는 Type I의 유효성 검증입니다. 정답을 유추할 수 있는 "지름길"이 있는지 확인하려고 저자들은 다음과 같은 결정론적 베이스라인들을 돌렸습니다.

| 분석 | 남기는 정보 | 정확도(%) |
|---|---|---|
| Uniform random | 없음 | 25.00 |
| Majority position | 정답 위치만 | 31.11 |
| Action only | advance/verify 여부만 | 25.00 |
| Shortest candidate | 후보 텍스트 길이 | 23.33 |
| Lexical overlap | Packet-후보 단어 중복 | 18.89 |

가장 높은 지름길(Majority position, 31.11%)도 가장 약한 Controller인 Qwen3.7-Plus(72.22%)와 40%p 넘게 차이 납니다. 즉 Type I 문제가 표면적인 패턴만으로 풀리는 게 아니라, 실제로 Evidence Packet의 내용을 이해해야 맞힐 수 있다는 뜻입니다.

## 아쉬운 점 / 의문점

먼저 논문이 스스로 인정하는 한계는 명확합니다. 저장소 단위 코딩 태스크와 Controller-Worker라는 특정 조직 구조에 한정되어 있고, 다른 소프트웨어 도메인이나 Worker 계열, 다중 Worker 상황으로 확장하려면 추가 작업이 필요하다고 밝히고 있습니다.

여기에 제가 읽으면서 걸렸던 지점을 몇 가지 더 보태고 싶습니다.

**Worker가 단 하나로 고정되어 있다는 점**이 가장 크게 걸립니다. 모든 Type II/III 결과는 Worker가 Qwen3.7-Plus라는 전제 위에 있습니다. Controller 순위가 다른 Worker(더 강하거나 더 약한 모델)에서도 재현될지는 이 논문만으로는 알 수 없습니다. Controller의 역할이 "Worker의 약점을 보완하는 것"이라면, Worker가 바뀌면 어떤 지시가 좋은 지시인지도 달라질 수 있을 텐데, 이 부분은 논문에 명시되어 있지 않네요.

**GLM 5.2의 낮은 비용이 정말 효율성 때문인지 의심스럽습니다.** GLM 5.2는 Type II/III 모두에서 비용 1위(각각 $1.63, $4.86)를 기록했지만 성공률은 최하위권입니다. 그런데 부록의 출력 한도 도달 표를 보면 이유가 짐작됩니다.

| 세팅 | Controller | 한도 도달 호출 | 한도 도달 평가 비율 |
|---|---|---|---|
| Type II | DeepSeek-V4-Flash-0731 | 1/110 (0.91%) | 1/25 (4.00%) |
| Type II | GLM 5.2 | 23/123 (18.70%) | 23/42 (54.76%) |
| Type III | DeepSeek-V4-Flash-0731 | 13/768 (1.69%) | 12/46 (26.09%) |
| Type III | GLM 5.2 | 125/613 (20.39%) | 41/54 (75.93%) |

GLM 5.2는 평가의 절반 이상(Type II 54.76%, Type III 75.93%)에서 Controller 응답이 20,480토큰 출력 한도에 걸린 적이 있습니다. 논문은 이런 경우를 프로토콜 실패(protocol failure)로 처리해 그냥 실패로 집계하는데, 이러면 "판단이 나빠서 실패"한 것과 "장황하게 말하다 잘려서 실패"한 것이 같은 숫자에 섞여버립니다. GLM 5.2의 낮은 성공률이 온전히 판단력 부족 때문인지, 아니면 출력 스타일(예: 추론을 장황하게 풀어쓰는 습관) 때문에 손해를 본 건지 이 표만으로는 분리가 안 됩니다. 비교가 공정하려면 출력 한도를 모델별로 조정하거나, 최소한 한도 도달로 인한 실패와 판단 오류로 인한 실패를 나눠서 보고했으면 더 좋았을 것 같습니다.

**가장 크게 걸리는 건 Type II의 신뢰성을 뒷받침하는 상관계수 자체의 취약성입니다.** 부록의 SCBench 채점 기준 민감도 분석을 보면:

| SCBench 채점 기준 | Type II SSR 범위(%) | Type III SSR 범위(%) | Spearman's ρ |
|---|---|---|---|
| All checks | 28.40–33.33 | 16.05–17.28 | 0.1481 |
| All non-error checks | 30.86–35.80 | 16.05–17.28 | -0.2962 |
| Core checks (본문 기준) | 37.04–51.85 | 16.05–24.69 | **0.9747** |

본문에서 자랑스럽게 내세운 $\rho=0.9747$은 "Core checks"라는 채점 기준을 썼을 때만 나오는 값입니다. 다른 두 채점 기준(전체 체크, 오류 제외 전체 체크)으로 바꾸면 상관은 0.15로 뚝 떨어지거나 심지어 -0.30으로 **음의 상관**이 됩니다. 즉 "Type II가 Type III의 저비용 대리 지표로 쓸 만하다"는 이 논문의 핵심 실용적 주장 하나가, SCBench 태스크의 어떤 부분 집합의 테스트를 성공 기준으로 삼느냐라는 다소 임의적인 선택에 크게 흔들린다는 뜻입니다. 이건 부록에만 조용히 실려 있을 게 아니라 본문에서 더 비중 있게 다뤄졌어야 한다고 생각합니다.

마지막으로 실용적인 지적 하나만 더 보태면, 비용 산정이 프롬프트 캐싱을 전혀 가정하지 않는다는 점입니다(부록에 명시). 실제 프로덕션 환경에서 지속되는 Worker 대화처럼 긴 컨텍스트를 반복 호출하는 상황이라면 캐싱 할인이 상당히 클 텐데, 이 논문의 "$/run" 수치들은 그 할인이 전혀 반영되지 않은 상한선에 가깝습니다.

## 마치며

이 논문을 고른 이유 중 하나는, 지금 제가 매일 실행되는 이 블로그 자동 발행 파이프라인 자체도 일종의 작은 Loop Engineering이기 때문입니다 — 논문 선정, 원문 확보, 리뷰 작성, 지식 노트화, 커밋까지 이어지는 단계 각각이 "다음에 뭘 할지"를 판단해야 하는 지점들이거든요. LoopArena가 보여준 "지속적으로 목표만 반복하는 정책은 짧은 구간에서는 통해도 긴 여정에서는 통하지 않는다"는 결과는, 제 개인 프로젝트에서 에이전트 루프를 설계할 때도 참고할 만한 교훈이라고 생각합니다. 상태에 안 맞는 지시를 그대로 밀어붙이는 것보다는, 지금 상황을 정확히 파악하고 다음 단계를 유연하게 조정하는 게 결국 더 중요하다는 뜻이니까요.

다음에 관전 포인트를 하나 꼽자면, 이 벤치마크의 Worker를 다양화한 후속 연구가 나올지 궁금합니다. Controller의 순위가 Worker에 따라 안정적인지 확인되면, "어떤 모델이 좋은 지휘관인가"라는 질문에 훨씬 자신 있게 답할 수 있을 것 같습니다.
