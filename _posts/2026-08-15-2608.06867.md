## 들어가며

어제(8월 14일) HuggingFace Daily Papers에서 89표를 받은 논문입니다. UIUC, Maryland, NTU, Purdue 등이 참여했고, 제목의 "Unified Infrastructure"라는 말 그대로 이 논문은 새로운 라우팅 알고리즘 하나를 제안하는 게 아니라 "LLM 라우팅"이라는 분야 자체를 정리하려는 논문입니다. 개인적으로 이 주제에 관심이 간 이유는, RouteLLM부터 GraphRouter, Router-R1까지 라우터 관련 논문들을 몇 개 읽어봤는데 그때마다 공식화 방식도, 평가 프로토콜도, 비교 대상 모델 풀도 다 달라서 "이 라우터가 저 라우터보다 낫다"는 주장을 검증하기가 항상 애매했기 때문입니다. 이 논문은 그 파편화 문제를 정면으로 다루면서, 실제로 16개 이상의 라우터를 하나의 인터페이스 아래 재구현하고 4,767개 쿼리로 구성된 벤치마크(xRouteBench)까지 함께 공개했습니다.

## 한눈에 보기

- **핵심 기여**: (1) LLM 라우팅을 context encoder $E_q$·model encoder $E_m$·scoring function $g$·decision rule $d$·learning signal $\mathcal{L}$ 5개 컴포넌트로 통일하는 공식화, (2) 이 공식화를 바탕으로 라우팅 supervision을 자동 구축하고 성능·비용을 동시에 평가하는 파이프라인, (3) 그 결과물인 벤치마크 xRouteBench(generic LLM tasks, memory, vision, time-series, personalized 5개 트랙, 4,767개 쿼리), (4) 16개 이상의 라우터를 하나의 `MetaRouter` 인터페이스로 재구현하고 Slack(OpenClaw)·ComfyUI·멀티에이전트 배포까지 지원하는 오픈소스 라이브러리 LLMRouter
- **성능**: 학습형 라우터가 가장 강한 고정 모델(Largest-LLM) 대비 평균 14.6% 상대적 향상. 비용 가중치가 커질수록 라우터 순위가 크게 뒤바뀜(가벼운 라우터가 유리해짐). 개인화 라우터는 페르소나 판정 기준으로도, 실제 사용자 234건의 선호 데이터 기준으로도 user-agnostic 라우터를 확실히 앞섬
- **한 줄 요약**: "라우터마다 딴 세상"이었던 분야를 하나의 수식과 하나의 코드베이스로 묶어보니, 모든 상황을 지배하는 라우터는 없고 각 라우터의 우위는 태스크와 비용 예산에 따라 계속 뒤바뀐다는 것을 실증한 인프라 논문

## 어떤 문제를 풀려고 했나

서론에서 저자들이 짚는 두 가지 장애물이 이 논문의 출발점입니다. 첫째, 기존 라우터들(binary router, cost-aware cascade, graph-based router, RL로 학습한 agentic router 등)이 전부 다른 형식론과 호환되지 않는 코드베이스로 구현되어 있고, 학습에 쓰는 supervision과 후보 모델 풀도 제각각이라 "성능 차이가 라우터 설계 때문인지, 실험 스택 전체가 달라서인지" 구분할 수 없다는 겁니다. 둘째, 라우터 평가는 단일 모델 평가보다 훨씬 부담이 큽니다. 라우팅 supervision을 만들려면 후보 풀 전체를 벤치마크 전체에 대해 실행해야 하는데, RouterBench나 RouterEval 같은 기존 벤치마크는 고정된 후보 풀에 대해 미리 계산된 응답만 제공하고 single-turn 텍스트 라우팅에 국한되어 있어서, 새로운 태스크나 후보 풀이 추가되면 처음부터 다시 만들어야 합니다.

그래서 이 논문의 목표는 명확합니다. 라우터를 다섯 개 컴포넌트로 분해할 수 있는 하나의 공식을 세우고, 그 공식 위에서 supervision 구축과 평가를 자동화하는 파이프라인을 만들고, 그 결과로 나온 벤치마크와 라이브러리를 공개하는 것입니다.

## 핵심 아이디어

### 라우팅을 하나의 순차적 의사결정 과정으로 본다

이 논문의 중심 주장은 겉보기에 전혀 다른 라우터들 — 약한 모델과 강한 모델 사이를 중재하는 binary router, 비용을 고려한 cascade, 그래프 기반 라우터, RL로 학습한 agentic 라우터 — 이 모두 하나의 순차적 의사결정 과정으로 표현될 수 있다는 것입니다. 스텝 $t$에서 라우터는 상태 $s_t = (q, u, h_t)$(쿼리 $q$, 선택적 사용자 컨텍스트 $u$, 지금까지 누적된 상호작용 히스토리 $h_t$)를 관찰하고 행동 $a_t$를 취합니다. 이 행동이 후보 $m$을 고르면($a_t = m$) 그 응답이 히스토리에 추가되고, 종료 행동($a_t = \bot$)을 고르면 지금까지 모은 응답들을 하나의 답으로 합쳐서 에피소드가 끝납니다. Single-turn 라우팅은 한 번 dispatch하고 바로 종료하는 특수 케이스입니다.

라우팅의 목표는 다음 목적함수를 최대화하는 정책 $\pi$를 찾는 것입니다.

$$
\pi^\star = \arg\max_{\pi}\; \mathbb{E}_{q,\, \tau \sim \pi} \big[\, \mathrm{perf}(y \mid q) - \lambda \cdot c(\tau) \,\big]
$$

$\mathrm{perf}(y \mid q)$는 정확도·F1·LLM judge 점수 같은 태스크별 품질 지표이고, $c(\tau)$는 라우팅 궤적 $\tau$에서 발생한 전체 비용(토큰 또는 금액), $\lambda \geq 0$는 성능과 비용 사이의 트레이드오프를 조절하는 계수입니다.

여기서 이 논문이 진짜로 하고 싶은 말은, 모든 라우터가 이 목적함수를 근사하는 다섯 개의 부품 — context encoder $E_q$, model encoder $E_m$, scoring function $g$, decision rule $d$, learning signal $\mathcal{L}$ — 으로 분해된다는 것입니다. $E_q$는 상태를 벡터로 임베딩하거나($k$NN, 판별 모델) 자연어 그대로 프롬프트에 넣고(cascade, 파인튜닝된 LM 라우터), $E_m$은 후보를 정적 메타데이터·과거 행동 이력·학습된 임베딩·언어로 서술한 설명 중 하나로 표현합니다. $g$는 이 둘의 호환성을 점수로 매기고, $d$는 그 점수를 실제 행동으로 바꾸는데, $\lambda = 0$일 때만 단순 $\arg\max$가 최적이고 비용을 고려하려면 임계값 기반 escalation이나 exploration 같은 별도 규칙이 필요합니다. $\mathcal{L}$은 이 부품들을 목적함수 쪽으로 맞추는 학습 신호로, supervised(포인트와이즈 정답 라벨), preference-based(쌍대 비교), agentic(RL 보상) 세 갈래로 나뉩니다.

다음은 이 통일된 공식화를 그림으로 정리한 것입니다.

![라우팅 통일 공식화 개요도](/assets/img/posts/2608.06867/fig1_unified.png)
_Figure 1. 왼쪽은 라우팅을 필요로 하는 세 가지 동기(비용 효율, 역량 매칭, 사용자 선호), 오른쪽 위는 세 라우터 계열이 상태의 어느 부분(쿼리·페르소나·히스토리)을 관찰하는지, 오른쪽 아래는 context encoder와 model encoder를 거쳐 라우터가 단일턴/멀티턴 응답을 만드는 실제 흐름._

오른쪽 위 박스를 보면 single-turn·multi-turn·personalized 세 계열의 차이가 정말로 "상태의 어느 부분을 보느냐" 하나로 요약됩니다. Single-turn은 쿼리만, multi-turn은 쿼리와 히스토리를, personalized는 여기에 페르소나까지 더해서 봅니다. 오른쪽 아래는 실제 라우팅 흐름인데, single-turn은 쿼리를 선택된 LLM 하나에 보내고 바로 답을 받는 반면, multi-turn은 서브쿼리를 여러 LLM에 순차로 보내면서 응답을 히스토리에 계속 쌓다가(보라색 화살표) 최종 답을 만듭니다. 개인적으로 이 그림에서 재미있었던 부분은, "개인화"가 별도의 알고리즘이 아니라 그냥 $E_q$에 사용자 조건을 끼워 넣는 것뿐이라는 저자들의 주장을 시각적으로 그대로 보여준다는 점입니다 — 나머지 컴포넌트는 그대로 두고 하나만 바꾼다는 이 모듈성이 논문 전체의 설계 철학입니다.

### 라이브러리 구조 — 사용자가 쓰는 건 다섯 줄뿐이다

공식화가 코드로 어떻게 내려오는지가 이 논문의 두 번째 축입니다. LLMRouter 라이브러리는 여섯 개 모듈(Data Engine, Router Library, Trainer, Route Engine, Evaluation, Deployment)로 구성되는데, 핵심 주장은 사용자가 새 라우터를 추가할 때 작성하는 코드는 딱 다섯 컴포넌트뿐이고 나머지 인프라(데이터 구축·학습·추론·평가·배포)는 그대로 재사용된다는 것입니다.

```python
class MyRouter(MetaRouter):
    def route_single(self, query):
        s = self.encode_state(query)              # E_q
        scores = self.score(s, self.models)        # E_m + g
        query["model_name"] = self.decide(scores)  # d
        return query

class MyRouterTrainer(BaseTrainer):
    def loss_func(self, outputs, batch):
        return my_objective(outputs, batch)        # L
```

`route_single`(또는 배치 버전 `route_batch`) 하나만 구현하면 되고, 학습 신호는 `BaseTrainer`의 `loss_func`로 분리되어 있습니다. 이 코드 자체는 단순하지만, 이게 의미하는 바는 라우터·후보 풀·학습 목적함수를 바꾸는 게 "재구현"이 아니라 "설정 파일 한 줄 교체"가 된다는 것입니다.

다음은 이 여섯 모듈이 어떻게 연결되는지 보여주는 시스템 개요도입니다.

![LLMRouter 라이브러리 아키텍처](/assets/img/posts/2608.06867/fig2_library.png)
_Figure 2. Data Engine(쿼리 수집→응답 수집→채점/가격 산정)이 만든 query-model matrix가 Router Trainer와 Route Engine을 거쳐 Evaluation(xRouteBench)과 Deployment(CLI, OpenClaw 서버, ComfyUI, 멀티에이전트)로 이어지는 구조._

왼쪽 아래 Data Engine을 보면 "쿼리 수집 → 응답 수집 → 채점/가격 산정"이라는 3단계로 하나의 query-model matrix를 만들고, 이게 위쪽 Router Trainer와 아래쪽 Route Engine 양쪽에 공급됩니다. 흥미로운 지점은 이 matrix가 학습 supervision이자 동시에 평가용 테스트베드로도 쓰인다는 겁니다 — 평가할 때는 그냥 전체 후보가 아니라 라우터가 고른 후보 하나만 실제로 호출한다는 차이뿐입니다. 오른쪽의 Deployment 박스에서 Command-Line, OpenClaw Server(Slack/Discord용), ComfyUI 인터페이스, Multi-Agent System 네 갈래로 나가는 것도 눈에 띄는데, 오프라인에서 학습·평가한 라우터를 코드 수정 없이 그대로 실서비스에 꽂을 수 있다는 뜻입니다. 다만 이 그림 자체는 논문 부록에 남아있는 저자 코멘트(공저자 Kunlun의 "이 그림 좀 개선이 필요하다", "benchmark가 왜 router trainer로 연결되는지 모르겠다")를 보면 저자들 스스로도 완전히 만족한 다이어그램은 아닌 것 같습니다. 여담이지만 이런 내부 코멘트가 그대로 남아있는 게 이 논문의 완성도에 대해 뭔가를 말해주는 것 같기도 합니다.

### xRouteBench — 라우팅 결정이 실제로 갈리는 지점만 모았다

세 번째 축은 벤치마크입니다. 기존 RouterBench나 RouterEval은 단일턴 텍스트 QA에 국한되어 있어서, "입력 토큰 비용이 지배적인 상황"이나 "후보 풀 일부만 입력을 처리할 수 있는 상황" 같은, 라우팅 결정이 실제로 갈리는 레짐을 다루지 못한다고 저자들은 지적합니다. xRouteBench는 이런 레짐을 다섯 트랙으로 모읍니다.

- **Generic LLM Tasks**: MMLU, GSM8K, MATH, HumanEval 등 13개 서브태스크(3,729개)를 하나의 라우팅 인터페이스 뒤에 놓아, 지식·commonsense·수학·코드처럼 서로 다른 역량을 요구하는 태스크를 텍스트 입력이라는 겉보기 균질함 아래 감춥니다.
- **Memory**: LoCoMo, LongMemEval처럼 긴 대화 히스토리에서 사실을 끌어와야 하는 태스크로, 토큰 비용이 답이 아니라 히스토리 자체에서 나옵니다.
- **Vision**: Geometry3K, MathVista(이미지), Charades-Ego(영상)로, 후보 풀 전체가 처리할 수 있도록 이미지를 텍스트로 변환(캡셔닝)한 뒤 라우팅합니다.
- **TimeSeries**: 시계열을 텍스트와 이미지 두 가지 인코딩으로 모두 렌더링해서, 라우터가 모델뿐 아니라 모달리티 인코딩까지 선택하게 만듭니다.
- **Personalized**: Chatbot Arena·MT-Bench 프롬프트를 PersonaHub에서 뽑은 200개 페르소나와 짝지어, 정답 하나가 아니라 페르소나 조건부 선호를 supervision으로 씁니다.

특히 인상적인 부분은 이 모든 트랙이 "같은 쿼리 스키마, 같은 supervision 포맷, 같은 평가 프로토콜"을 공유하도록 설계됐다는 점입니다. 비전과 시계열 트랙에서도 이미지나 시계열을 미리 고정된 vision-language 모델(Gemma-3-27B-IT)로 텍스트 설명으로 바꿔서, 텍스트만 처리하는 후보 모델도 똑같은 쿼리에 대해 경쟁할 수 있게 만듭니다. 이렇게 하면 "라우팅 성능"과 "지각(perception) 성능"이 뒤섞이지 않는다는 게 저자들의 논리인데, 반대로 말하면 원본 이미지/시계열이 담고 있었을 정보가 캡셔너의 병목을 거치면서 손실됐을 가능성도 있다는 뜻이라, 이 설계가 완전히 공짜는 아니라고 생각합니다.

### 비용이 개입하면 순위표가 통째로 뒤집힌다

이 논문에서 가장 흥미로웠던 부분은 비용 가중치 $\beta$를 0에서 0.8까지 올리면서 각 라우터의 순위가 어떻게 바뀌는지 본 다음 그래프입니다.

![비용 가중치에 따른 라우터 순위 히트맵](/assets/img/posts/2608.06867/fig8_rank_heatmap.png)
_Figure 8. Generic LLM Tasks, Memory, Vision, TimeSeries 네 트랙에서 비용 가중치 β가 커질수록(왼쪽→오른쪽) 각 라우터의 순위(작을수록 좋음)가 어떻게 이동하는지 보여주는 히트맵._

이 그림은 각 칸의 숫자가 그 라우터의 순위이고, 진한 파랑일수록 좋은 순위(1위에 가까움)입니다. 가로로 읽으면 라우터 하나가 $\beta$가 커지는 동안 어떻게 흔들리는지 보이는데, 예를 들어 Generic LLM Tasks 열에서 RouterDC는 $\beta=0$일 때 1위였다가 $\beta=0.8$에서는 10위(11개 중)로 추락합니다. 반대로 Vision 열의 MLPRouter는 $\beta=0$에서 10위(거의 꼴찌)였다가 $\beta \geq 0.4$부터는 계속 1위를 유지합니다. 즉 "성능만 볼 때 나쁜 라우터"가 "비용까지 고려하면 최선의 선택"으로 바뀌는 경우가 실제로 존재한다는 겁니다. 이건 단순히 "비싼 모델을 쓰는 라우터가 비용이 개입되면 손해를 본다"는 당연한 이야기를 넘어서, 애초에 quality-only 순위표만 보고 라우터를 고르면 안 된다는 실무적 메시지로 읽힙니다.

### 개인화 — 시뮬레이션과 실제 사용자가 다른 답을 준다

개인화 트랙에서는 GMTRouter(68.78)가 PersonalizedRouter(67.86)와 최고 user-agnostic 라우터인 EloRouter(66.40)를 근소하게 앞섭니다. 그런데 저자들이 실제 Slack 배포(OpenClaw)를 통해 15명 사용자로부터 40개 세션, 234건의 쌍대 선호 데이터를 모아 다시 평가하자 순위가 달라집니다. PersonalizedRouter가 83.05로 1위, EloRouter가 82.20으로 2위인 반면, 시뮬레이션에서 1위였던 GMTRouter는 70.70으로 6위까지 떨어집니다. 저자들 스스로도 "시뮬레이션 순위가 완전히 전이되지는 않는다"고 인정하는데, 이건 페르소나 조건부 LLM judge로 만든 supervision과 실제 사람의 선호가 상당히 다른 것을 최적화하고 있을 수 있다는 뜻이라 개인적으로 가장 눈여겨볼 결과라고 생각합니다. 다만 234건이라는 표본 크기, 8개 테스트 세션이라는 규모는 이 결론의 통계적 안정성을 낮추는 요인이라 그대로 받아들이기보다는 "방향성 신호" 정도로 보는 게 맞을 것 같습니다.

### 멀티에이전트 시스템 안에서도 라우팅이 이득이다

마지막으로 흥미로운 확장은, 멀티에이전트 시스템(MAS)의 각 노드(planner, executor, summarizer 등)마다 공유 모델 하나를 쓰는 대신 노드별로 다른 모델을 라우팅하는 실험입니다. 다섯 가지 협업 토폴로지에서 이를 테스트합니다.

![다섯 가지 멀티에이전트 협업 토폴로지](/assets/img/posts/2608.06867/fig9_multiagent.png)
_Figure 9. (a) Star(중앙집중형), (b) Tree(계층적 위임), (c) Graph(peer-to-peer), (d) Chain(순차 협업), (e) Plan-Exec-Sum(planner-executor-summarizer)._

각 토폴로지에서 planner·actor(또는 executor)·summarizer 역할의 프롬프트는 서로 완전히 다른 성격(계획 수립 vs. 실행 vs. 요약/검증)을 갖기 때문에, 일반 쿼리로 학습한 라우터가 이런 특이한 프롬프트에도 일반화되는지가 관건입니다. 결과적으로 학습형 라우터 7개 중 6개가 "항상 최대 모델 사용"(평균 71.48) 대비 더 나은 평균 성능을 냈고, 가장 좋은 MFRouter는 76.48까지 올라갔습니다. Star 토폴로지에서 RouterDC(77.60)가 강한 반면 Graph 토폴로지에서는 MFRouter(81.00)가 강한 것처럼, 여기서도 "모든 토폴로지를 지배하는 라우터는 없다"는 같은 패턴이 반복됩니다.

## 아쉬운 점 / 의문점

몇 가지 걸리는 지점이 있습니다.

첫째, multi-turn 라우터(Router-R1, $k$NN-MultiRound, LLM-MultiRound)의 성능이 rule-based baseline보다도 한참 낮은 게(22~23% vs 37~39%) 좀 의아합니다. 논문은 이걸 "베이스 모델(Qwen2.5-3B-Instruct)의 역량에 성능이 민감하기 때문"이라고 설명하는데, 그렇다면 이건 라우팅 알고리즘의 실패가 아니라 실험 설정(작은 베이스 모델을 고정으로 쓴 것)의 문제일 수도 있습니다. multi-turn 라우팅 자체가 원래 잘 안 되는 건지, 아니면 이 논문의 벤치마크에서 쓴 베이스 모델이 유독 약해서인지는 이 결과만으로 확신하기 어렵습니다. 더 큰 베이스 모델로 multi-turn 라우터를 돌린 ablation이 있었다면 이 논쟁이 정리됐을 텐데 그런 실험은 보이지 않습니다.

둘째, 5개 컴포넌트 공식화 자체를 직접 검증하는 실험이 없습니다. 이 논문은 "기존 라우터를 이 틀로 재분류할 수 있다"는 걸 보여주는 데는 성공했지만, 이 공식화가 "옳은" 분해라는 걸 입증하는 ablation — 예를 들어 같은 $E_q, E_m, g$를 고정하고 $d$만 바꿔서 성능이 어떻게 변하는지, 혹은 반대로 컴포넌트를 섞어서(mix-and-match) 새로운 조합이 기존 라우터보다 나은지 — 은 제시되지 않습니다. 그래서 이 논문의 가장 실질적인 기여는 "통일된 이론"보다는 "16개 라우터를 공정하게 비교 가능하게 만든 인프라와 벤치마크" 쪽이라고 보는 게 더 정확할 것 같습니다.

셋째, 후보 모델 풀이 18개 오픈웨이트 모델(Together API, NVIDIA NIM 경유)로만 구성되어 있고, GPT-5나 Claude, Gemini 같은 프론티어 프로프라이어터리 API는 빠져 있습니다. 실무에서 라우팅이 정말 절실한 시나리오 중 하나가 "비싼 프론티어 모델과 저렴한 오픈웨이트 모델 사이의 선택"인데, 이 벤치마크는 오픈웨이트 모델들 사이의 라우팅만 다루기 때문에 성능 격차와 비용 격차 둘 다 실제 프로덕션 환경보다 작게 나타날 가능성이 있습니다.

넷째, 라우터 자체를 호출하는 데 드는 지연 시간이나 연산 비용은 목적함수 $c(\tau)$에 포함되지 않는 것으로 보입니다. GraphRouter처럼 쿼리-모델 그래프에 메시지 패싱을 하는 라우터와 EloRouter처럼 쿼리를 아예 안 보는 라우터는 추론 비용 자체가 크게 다를 텐데, 이 차이가 성능-비용 트레이드오프 분석에 반영되어 있는지는 논문에 명시되어 있지 않습니다.

## 마치며

전체적으로 이 논문의 가치는 "새로운 라우팅 알고리즘"이 아니라 "라우팅 연구를 검증 가능하게 만드는 공용 인프라"에 있다고 느꼈습니다. 개인적으로는 지금 작은 규모로 진행 중인 프로젝트에서 비용 절감을 위해 모델을 선택적으로 쓰는 로직이 필요한데, 처음부터 라우터를 새로 짜기보다는 이 라이브러리의 `MetaRouter` 인터페이스 위에 간단한 $k$NN이나 EloRouter부터 붙여보고 비용-성능 커브를 직접 그려보는 것부터 시작해볼 만하다는 생각이 들었습니다.
