## 들어가며

HF Daily Papers에서 272표를 받은 논문입니다. 저자 소속이 Qwen Team(Alibaba)과 Tsinghua University인데, 최근 터미널 코딩 에이전트(Claude Code, Terminus2 같은) 학습 데이터를 어떻게 대량으로 만들 것인가가 업계의 공통 숙제가 되어 있다 보니 이 논문이 던지는 아이디어가 꽤 신선했습니다.

핵심 관찰은 단순합니다. 지금 인터넷에는 코딩 에이전트가 실제로 작업한 기록, 즉 trajectory(어떤 파일을 읽고, 어떻게 고치고, 어떤 명령을 실행했는지의 로그)가 이미 잔뜩 쌓여 있습니다. 그런데 이 trajectory 자체는 학습 데이터로 쓰기엔 한계가 뚜렷합니다. 그걸 만든 모델의 실력만큼만 정확하고, 이미 정답이 박제된 "죽은" 기록이라 재검증도 안 되고 재질문도 안 됩니다. 저자들의 통찰은 "trajectory 안에는 사실 그게 실행됐던 환경(environment)의 정보가 고스란히 남아있다"는 겁니다. `Read`가 파일 내용을 보여주고 `Write`/`Edit`가 워크스페이스가 어떻게 바뀌었는지 보여주니, 이걸 역재생하면 원래 환경을 상당 부분 되살릴 수 있다는 거죠. 그렇게 살려낸 환경은 죽은 기록과 달리 다시 질문을 던질 수 있고, 다른(더 강한) 모델로 다시 풀게 할 수 있고, 검증기로 채점할 수 있는 "살아있는" 자원이 됩니다.

## 한눈에 보기

- **핵심 기여**: 코딩 에이전트 trajectory를 결정론적 재생(replay)과 에이전트 기반 보완(completion)으로 실행 가능한 워크스페이스로 복원하고, 그 위에서 원래 의도 재구성(Intent Recovery)·같은 워크스페이스 내 새 문제(Single-WS)·여러 워크스페이스를 엮은 문제(Cross-WS)·다회차 대화형 문제(Multi-Round)의 4가지 방식으로 새 학습 데이터를 재생산하는 파이프라인
- **성능**: 이렇게 만든 3.2만 건으로 Qwen3.5-27B를 SFT하면 Terminal-Bench 2.1이 46.2%→58.1%(+11.9p), EvoCode-Bench v2(다회차 벤치마크)의 MT@4가 6.3%→20.1%(+13.8p)로 오르고, 같은 조건의 기존 데이터 합성 방법들을 전부 앞선다고 합니다
- **한 줄 요약**: trajectory를 모방하지 말고, trajectory가 남긴 흔적으로 환경을 복원해서 다시 풀게 하라

## 어떤 문제를 풀려고 했나

터미널/코딩 에이전트를 post-training 시키려면 "풀 수 있고, 채점할 수 있는" 실행 환경이 대량으로 필요합니다. 그런데 지금까지의 환경 구축 방식은 논문이 세 갈래로 정리합니다.

1. **저장소 기반(repository-based)**: 실제 git 히스토리에서 버그가 고쳐지기 직전 커밋으로 되돌려 환경을 만들고, 원래 버그 리포트를 태스크로, 딸려온 테스트를 검증기로 씁니다(SWE-Gym, R2E-Gym 등). 현실적이지만 "고쳐진 버그"라는 좁은 태스크 유형에 갇힙니다.
2. **퍼터베이션(perturbation)**: 잘 돌아가는 저장소에 일부러 버그를 주입해서 실패하게 만듭니다(SWE-smith, CLI-Gym). 적은 저장소로 많은 태스크를 뽑을 수 있지만 전부 "고치기" 태스크이고, 주입 가능한 버그 종류로 다양성이 제한됩니다.
3. **태스크 조건부 합성(task-conditioned synthesis)**: 카테고리나 스킬 그래프를 정해두고 태스크와 환경을 처음부터 같이 생성합니다(TMax, CLI-Universe, SkillSynth). 커버리지는 통제할 수 있지만 결국 생성기가 만든 "작고 깔끔한" 가짜 프로젝트라 리얼함이 떨어집니다.

세 갈래 모두 공통점이 있습니다. 환경을 "이미 존재하는 저장소"에서 시작하거나 "처음부터 새로 생성"하는 두 축 사이에서만 움직인다는 점입니다. 저자들은 여기에 세 번째 축을 제안합니다 — **trajectory 자체를 거꾸로 재생해서 환경을 복원하는 것**. 이미 쌓여있는 방대한 에이전트 실행 로그를 그대로 재활용 자원으로 본다는 점에서, "환경을 어디서 구할 것인가"라는 질문 자체를 바꾼 셈입니다.

## 핵심 아이디어

다음은 Terminal-Universe 파이프라인 전체를 요약한 그림입니다.

![Terminal-Universe 개요](/assets/img/posts/2609.04148/fig1-overview.png)
_Figure 1. 왼쪽: 기존 방식은 환경→trajectory 방향으로만 흘렀는데(rollout), 이 논문은 반대로 trajectory→환경(reconstruct)을 복원한 뒤 다시 trajectory를 만든다(reuse). 가운데: 복원은 재생(Stage 1)과 보완(Stage 2) 2단계. 오른쪽: 복원된 환경을 Single-WS/Cross-WS/Multi-Round 세 방식으로 다시 질문한다._

왼쪽 패널이 이 논문의 태도를 한 장으로 보여줍니다. 기존 연구는 환경(Env)이 있으면 그걸 굴려서(rollout) trajectory를 뽑는 방향으로만 생각했는데, 이 논문은 이미 존재하는 trajectory를 거슬러 올라가 환경을 재구성(Reconstruct)하고, 그걸 다시 활용(Reuse)해 새 trajectory를 만듭니다. 화살표 방향을 뒤집었을 뿐인데 "환경이 부족하다"는 문제 자체가 "이미 쌓인 trajectory 더미를 자원으로 못 쓰고 있었다"는 문제로 재정의됩니다.

### 1) 환경 복원 — 재생하고, 채워 넣고, 걸러낸다

복원은 3단계입니다.

**Stage 1: 결정론적 재생(deterministic replay).** trajectory에 기록된 읽기/쓰기/편집 명령을 시간 순으로 그대로 재생해서, 에이전트가 손대기 전 파일의 최초 상태를 복구합니다. 에이전트가 새로 만든 파일이나 그 이후의 수정은 전부 제외합니다 — 그래야 워크스페이스가 "아직 안 풀린 상태"로 시작하니까요. 문제는 trajectory가 에이전트가 실제로 건드린 파일만 보여준다는 겁니다. 안 건드린 파일, 암묵적인 시스템 의존성, 외부 네트워크 자원은 흔적이 안 남습니다. 그래서 이 단계로 복원한 워크스페이스 $\widehat{E}_0$는 필연적으로 "부분적"입니다.

**Stage 2: 에이전트 기반 보완(agentic completion).** 부분적인 워크스페이스와 복원된 태스크를 받은 보완 에이전트가 빠진 파일을 만들고, 미완성 파일을 채우고, 의존성을 복구합니다. 다만 태스크를 "풀지는" 않아야 합니다 — 정답을 흘리면 안 되니까요. 이 역할 분리가 재미있는 지점인데, "문제를 풀 수 있게는 만들되 풀어주지는 마라"는 상당히 미묘한 지시를 프롬프트 하나로 강제하고 있습니다. 실제로 무작위 샘플 30개를 사람이 검수했을 때 22개는 태스크에 필요한 지원 파일만 담고 있었고, 나머지 8개는 불필요한 파일이 좀 섞여 있었지만 30개 전부에서 정답이 새어나간 경우는 없었다고 합니다.

**Stage 3: 환경 필터링.** 읽기 전용 셸/파일 도구를 가진 판정 에이전트가 완성된 워크스페이스를 보고 "이 태스크를 풀기에 프로젝트 맥락이 충분한가"를 이진 판정합니다. 충분하다고 판정된 것만 다음 단계로 넘어갑니다.

아래는 이 3단계 전체와, 복원된 환경에 다시 질문을 던지는 4가지 방식(Intent Recovery / Single-WS / Cross-WS / Multi-Round)을 한 번에 보여주는 상세 그림입니다.

![Terminal-Universe 프레임워크 상세](/assets/img/posts/2609.04148/fig2-framework.png)
_Figure 2. 왼쪽: trajectory 재생 → 완성된 워크스페이스 → 태스크 충분성 필터. 오른쪽 위부터: Single-workspace(한 워크스페이스 탐색해서 새 문제 생성), Cross-workspace(워크스페이스 간 의존 관계를 찾아 두 저장소를 엮은 문제 생성), Multi-Round(초기 질문 이후 유저 에이전트가 후속 요구를 이어붙임)._

이 그림에서 눈여겨볼 부분은 왼쪽 아래 "Completed workspace" 박스입니다. `replayed`로 표시된 것들(`config.json`, `linux_build.sh`, `sample1-3.txt`)은 원래 trajectory에서 재생된 것이고, `+`가 붙은 것들(`schemas/`, `scripts/`, `src/`, `Makefile`, `pyproject.toml`)은 Stage 2에서 새로 채워 넣은 것들입니다. 재생만으로는 파일 몇 개짜리 앙상한 뼈대였는데, 보완을 거치면 진짜 프로젝트처럼 보이는 구조가 된다는 걸 시각적으로 잘 보여줍니다.

오른쪽의 Cross-workspace 부분도 짚을 만합니다. ①워크스페이스마다 도메인·언어·구현된 기능을 프로파일링하고 ②TF-IDF로 비슷한 워크스페이스 후보를 뽑은 뒤 LLM 판정기로 "A에는 없는데 B에는 있는 기능"이라는 방향성 있는 의존 관계를 찾고 ③그 기능 격차를 메우는 태스크를 만듭니다. 이때 대상(target) 워크스페이스는 쓰기 가능하게, 참조(reference) 워크스페이스는 읽기 전용으로 별도 경로에 마운트해서, 에이전트가 참조 코드를 실제로 읽고 이해해서 옮겨와야만 풀리게 강제합니다. 두 개의 별개 프로젝트를 가져다가 억지로 "A가 B를 참조해야 하는 상황"을 만든다는 점에서, 실제 개발에서 "다른 레포의 구현을 참고해서 우리 프로젝트에 이식한다"는 흔한 상황을 재현하려는 시도로 보입니다.

Multi-Round 쪽은 유저 에이전트가 요구사항 트래커를 유지하면서 라운드마다 요구를 갱신하고, 매 라운드마다 별도 검증기가 채점한 뒤 그 결과를 자연어 피드백으로 바꿔 코딩 에이전트에게 전달하는 구조입니다. 코딩 에이전트는 테스트 스크립트나 트레이스백을 직접 보지 못하고, 오직 "이 부분이 아직 이상해요" 같은 사용자 관점의 불만만 받습니다. 실제 세션 예시 하나를 표로 옮기면 이렇습니다.

| 라운드 | 유저 요청 요지 |
|---|---|
| 초기 요청 | 하드코딩된 입출력 경로를 명령줄 인자로 바꿔달라 |
| 1: Extension | 파일이 계속 커지니 증분(incremental) 처리 모드를 추가해달라 |
| 2: Revision | 행 개수 집계는 맞는데 값 자체가 이상하다 — 스케일링이 잘못된 것 같다 |
| 3: Extension | 센서 임계값 벗어남을 알려주는 규칙 기반 알림 엔진을 추가해달라 |
| 4: Conflict | 알림 기록 방식을 "매번 덮어쓰기"에서 "이력 누적"으로 바꿔달라 |
| 5: Extension | 쌓인 이력을 요약해서 보여주는 리포트 명령을 추가해달라 |
| 6: Extension | 상태 불일치를 감지만 하지 말고 자동으로 복구까지 하게 해달라 |

라운드 2가 "Revision"으로 분류된 이유는 직전 요구(증분 처리)가 버그로 실패했기 때문이고, 라운드 4가 "Conflict"로 분류된 이유는 기존 사양(덮어쓰기)을 뒤집는 요구이기 때문입니다. 이렇게 라운드 성격 자체를 실제 결과(성공/실패/사양 변경)에서 자연스럽게 결정하게 만든 점이 눈에 띕니다 — 미리 "몇 번째 라운드는 conflict여야 해" 같은 비율을 정해두지 않았다고 합니다.

### 2) 얼마나 많이 걸러지는가 — 함수가 아니라 깔때기

이 파이프라인이 실제로 얼마나 "수율이 낮은" 작업인지 보여주는 그림이 있습니다.

![복원 파이프라인의 깔때기](/assets/img/posts/2609.04148/fig5-funnel.png)
_Figure 5. 35만 9,593개의 원본 trajectory에서 시작해 최종적으로 3만 7,273개(약 10.4%)의 "태스크 충분" 환경만 살아남는 과정._

왼쪽부터 따라가 보면, 35.9만 개 trajectory 중 무려 29.1만 개(81%)가 "재생 복잡도 부족"이라는 이유로 애초에 탈락합니다. 파일을 별로 안 건드렸거나 명령어 위주라 재구성할 근거가 부족하다는 뜻입니다. 살아남은 6.8만 개 중에서도 오염(contamination) 필터링과 저장소 단위 중복 제거로 2.8만 개가 또 걸러지고, 남은 4만 개에 대해 충분성 판정을 돌려 최종 3.7만 개(전체의 약 10.4%)만 "태스크 충분" 판정을 받습니다. 개인적으로는 이 수치가 이 논문에서 가장 솔직한 부분이라고 느꼈습니다. "trajectory를 재활용한다"는 아이디어 자체는 그럴듯하지만, 실제로는 10개 중 9개는 재활용이 안 되는 걸 인정하고 있다는 뜻이니까요. 다르게 보면, 이 정도 tail이 있다는 건 애초에 소스가 되는 trajectory 자체가 훨씬 더 많아야 이 파이프라인이 규모의 경제를 낼 수 있다는 뜻이기도 합니다.

살아남은 워크스페이스가 보완 단계를 거치며 얼마나 "실해지는지"도 수치로 보여줍니다.

_Figure 3. 재생 직후($\widehat{E}_0$, 빈 동그라미)와 에이전트 보완 후($\widehat{E}$, 채워진 초록 점)의 워크스페이스당 파일 수·전체 텍스트 줄 수·코드 줄 수 비교._

터미널 계열 워크스페이스는 재생 직후 평균 파일 2.9개, 텍스트 90줄짜리 앙상한 뼈대였다가 보완 후 파일 22.4개(7.7배), 텍스트 5,761줄(64배)로 불어납니다. 흥미로운 건 코드 줄 수 증가폭(11.7배)이 텍스트 줄 수 증가폭(64배)보다 훨씬 작다는 점인데, 이는 보완 단계가 실제 로직 코드보다는 설정 파일·픽스처·데이터처럼 "프로젝트가 있어 보이게 만드는" 주변 맥락을 주로 채워 넣는다는 뜻으로 읽힙니다. 반면 SWE(소프트웨어 엔지니어링) 계열은 애초에 실제 저장소에서 나온 것이라 재생 단계부터 이미 더 풍부하고(파일 5.6개, 코드 487줄), 배율도 상대적으로 덜 극적입니다. 재생과 보완이 서로 다른 일을 하고 있다는 게 이 그림 하나로 잘 드러납니다.

### 3) 검증 — 통과한 것만 남긴다

Single-WS와 Cross-WS 태스크는 각각 컨테이너 안에서 전용 에이전트가 직접 pytest 스위트를 작성해서 붙입니다. 이후 교사 모델(Qwen3.7-Max, xhigh 추론 강도)이 Claude Code 스캐폴드 위에서 태스크를 풀고, 그 결과가 테스트를 전부 통과해야만 학습 데이터로 채택됩니다. Multi-Round는 라운드 단위로 선별하는데, 종료된 세션에서 연속으로 실패한 꼬리 라운드를 잘라내고, 검증 통과 라운드가 최소 2개 이상 남는 세션만 채택합니다. 실패했다가 회복하는 라운드는 일부러 남겨서 "에러를 진단하고 고치는" 감독 신호로 활용한다고 합니다.

### Ablation이 말해주는 것들

- **재생만 vs 재생+보완**: Intent Recovery 데이터로 비교했을 때 재생만 한 워크스페이스로 학습하면 48.7점, 보완까지 거친 워크스페이스로 학습하면 52.9점입니다(게다가 분산도 ±3.5→±1.4로 안정적). 앞서 본 사실성 판정 결과(재생만으로는 터미널 워크스페이스의 40.2%만 충분, 보완 후 93.5%)와 정확히 맞아떨어집니다.
- **원본 trajectory 모방 vs 재구성 후 재풀이**: 같은 소스에서 나온 원본 trajectory로 SFT하면 36.7점인데, 환경을 복원해서 더 강한 교사 모델로 다시 풀게 한 데이터로 SFT하면 52.1점입니다. 저자들의 핵심 주장 — "trajectory를 베끼지 말고 환경을 되살려 다시 풀어라" — 을 가장 직접적으로 뒷받침하는 수치입니다.
- **검증기 필터링**: Single-WS는 필터링 여부와 무관하게 비슷한 성능(56.0 vs 56.4)을 내지만 Cross-WS는 필터링 없이 쓰면 오히려 떨어집니다(53.2 vs 55.4). 태스크가 어려워질수록 교사 모델이 실패한 trajectory를 그냥 섞어 넣는 게 독이 된다는 뜻으로 읽힙니다.
- **데이터를 어디에 더 쓸지(같은 예산 두 배 실험)**: 환경을 두 배로 늘리면 53.2→56.0으로 오르지만, 환경 수는 그대로 두고 워크스페이스당 질문을 두 배로 늘리거나(53.8) 같은 질문에 정답을 두 배로 늘리면(53.9) 거의 안 오릅니다. "새 워크스페이스 하나가 새 질문 하나보다 값지다"는 결론인데, 이는 이 논문 전체의 동기("환경을 더 많이 복원하자")를 정량적으로 뒷받침하는 결과이기도 합니다.

## 아쉬운 점 / 의문점

논문이 스스로 인정한 한계부터 보면, ① 모든 워크스페이스를 특화 이미지가 아니라 표준 Ubuntu 24.04 컨테이너에 올리기 때문에 특수한 시스템 의존성이나 복잡한 빌드 단계가 필요한 경우 재현도가 떨어질 수 있고, ② 복원된 워크스페이스의 도메인·언어 분포가 결국 소스 trajectory 풀의 분포에 갇혀 있으며(실제로 Python이 84.7%), ③ 태스크 생성·풀이·검증을 전부 교사 모델 하나(Qwen3.7-Max)가 담당해서 그 모델의 실력 한계가 그대로 데이터 품질의 한계가 될 수 있다고 밝힙니다.

리뷰어로서 몇 가지 더 걸리는 지점이 있습니다.

첫째, "Deterministic replay"라는 이름이 조금 과장돼 보입니다. 재생 자체는 결정론적이지만, 그다음 Stage 2(agentic completion)는 LLM이 파일을 새로 만들어내는 확률적 과정이고, 논문이 강조하는 성능 향상의 대부분이 사실 이 확률적 단계에서 나옵니다. 재생만으로는 태스크 충분성이 20~40%에 그치고, 실질적으로 쓸모 있어지는 건 보완을 거친 뒤라는 걸 생각하면 "환경을 trajectory에서 복원했다"기보다는 "trajectory를 뼈대 삼아 LLM이 프로젝트를 새로 지어냈다"에 더 가깝지 않나 싶습니다. 보완 에이전트가 만든 파일이 정말 "그 trajectory가 원래 실행됐던 환경"과 얼마나 비슷한지는 검증할 방법이 없다는 점도(어차피 원본 환경은 사라졌으니) 근본적인 한계로 남습니다.

둘째, 완성 품질 검증이 30개 샘플의 수작업 검수뿐이라는 점이 아쉽습니다. 3만 7천 개 환경 중 30개(0.08%)만 사람이 봤다는 뜻인데, "정답 유출이 없었다"는 결론을 이 정도 샘플로 일반화하기엔 근거가 얇습니다. 특히 보완 에이전트와 태스크 생성 에이전트가 같은 계열의 모델이라면, 우연이 아니라 체계적으로 힌트를 흘리는 실패 모드가 있어도 30개로는 못 잡아낼 가능성이 있습니다.

셋째, Cross-WS 결과 해석에서 "3개 카테고리가 2.1~2.5점 하락했지만 8개 이하 태스크짜리 카테고리라 런-투-런 변동 범위 안"이라고 설명하는 부분은, 뒤집어 말하면 상승분(모델 훈련 +15.0, 디버깅 +10.0)도 같은 이유로 노이즈일 수 있다는 뜻입니다. 태스크 수가 적은 카테고리에서 좋은 쪽 변화는 "진짜 개선"으로, 나쁜 쪽 변화는 "노이즈"로 부르는 건 비대칭적인 해석으로 보입니다.

넷째, 코드나 데이터셋 공개 여부가 논문에 명시되어 있지 않습니다. HuggingFace Daily Papers 페이지에도 GitHub 저장소 링크가 없어서, 이 파이프라인을 직접 돌려보기는 당장 어려워 보입니다.

## 마치며

개인적으로 이 논문에서 가장 재밌었던 지점은 "trajectory와 environment는 같은 사건의 두 가지 관점"이라는 프레이밍 자체입니다. 지금까지 에이전트 학습 데이터 이야기는 거의 항상 "환경을 어떻게 더 잘/많이 만들 것인가"였는데, 이 논문은 "우리가 이미 만들어 놓은 trajectory 더미 자체가 환경의 압축된 인코딩이다"라고 관점을 뒤집었습니다. 데이터를 새로 만드는 대신 이미 있는 부산물에서 자원을 뽑아내는 방식이라, 코드 공개가 안 되어 있어도 아이디어 자체는 다른 세팅(예: 웹 에이전트, GUI 에이전트의 액션 로그)에도 응용해볼 만하다고 생각합니다. 다만 앞서 지적했듯 "결정론적 재생"이라는 이름값에 비해 실제 무게중심은 에이전트 보완 단계의 생성 품질에 쏠려있다는 점은 후속 연구에서 더 파고들 만한 지점 같습니다. 다음에 이 계열 논문을 볼 때는 "보완 에이전트가 만든 콘텐츠가 원본과 실제로 얼마나 가까운가"를 어떻게 검증하는지를 눈여겨보려 합니다.
