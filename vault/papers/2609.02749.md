# 모델도 하니스도 아닌 '요령'이 빠져 있었다 — Repo-To-Skill: Distilling GitHub Repositories Into AI4AI Skills

> 원제: 모델도 하니스도 아닌 '요령'이 빠져 있었다 — Repo-To-Skill: Distilling GitHub Repositories Into AI4AI Skills
> 리뷰: [블로그 전문](https://rina-oo.github.io/posts/2609.02749/)

## TL;DR
자율 ML 리서치 에이전트를 모델 $M_\theta$ + 하니스 $H$의 2요소 관점에서 운영 지식(operational knowledge) $\mathcal{K}$를 더한 3요소 $\mathcal{A}_{res}=(M_\theta,H,\mathcal{K})$로 재정의한다. $\mathcal{K}$는 Anthropic Agent Skills 스펙을 따르는 스킬 집합으로 구현되며, scope→ground→construct→verify 4단계 파이프라인(DisCo)으로 레포·논문·태스크에서 자동 증류된다. 이를 1,000개 ML 레포에 적용해 5,000개 이상의 검증된 스킬을 가진 AREX-Skill 라이브러리(20 영역·178 패밀리)를 구축했고, 같은 Codex+GPT-5.5 백본·하니스·실행 예산을 고정한 채 스킬만 붙여 MLE-bench +134.3%, PaperBench +34.4%, FrontierCS +9.2%, PassNet +14.0%의 성능 향상을 보였다.

## 핵심 기여
- 운영 지식을 모델·하니스와 구별되는 세 번째 층으로 정식화: 하니스는 "어떻게 탐색할지", $\mathcal{K}$는 "무엇을 고려할지"를 특화한다는 역할 분리
- 스킬을 3층 구조(SKILL.md=지식 인터페이스, references/=지식 기반, scripts/=실행 인터페이스)로 정의하고, 여러 스킬을 진입점+링크로 묶는 skill graph $\mathcal{G}=(\mathcal{S},\mathcal{L})$ 개념 도입
- scope→ground→construct→verify 4단계 증류 파이프라인을 task-agnostic(소스가 앵커)과 task-oriented(태스크가 앵커) 두 형태로 통일적으로 적용, verify 단계(assertion 테스트·실제 실행 검증·국소 리페어)로 "요약"과 "증류"를 구분
- MLE-bench용 스킬은 실행 가능한 코드 없이 서술적 지침만 담도록 설계해, 벤치마크 실행 시점에 에이전트가 매번 새로 구현하게 강제 — 고정 솔루션 재생 문제를 회피
- 1,000개 레포 → 5,353개 스킬, 20 영역·178 패밀리 라우터로 조직된 AREX-Skill 라이브러리 공개(레포당 평균 $40 구성 비용), MLE-bench/PaperBench/FrontierCS/PassNet 4개 벤치마크에서 통제 비교로 일관된 개선 확인

## 한계
- 별도 Limitations 섹션 부재. 레포 업데이트에 따른 스킬 재증류·유효기간 논의 없음(스냅샷 시점 스킬의 장기 유효성 불명)
- MLE-bench 리더보드 비교에서 공개 1위(Gemini-3-Pro/Claude-Opus-4.6 기반)와 저자 시스템(GPT-5.5)의 백본이 다름 — 스킬 유무 통제 비교(Codex vs Codex+Skill) 자체는 공정하나 "공개 1위보다 우위"라는 서사는 백본·하니스가 동시에 다른 비교라 프레이밍이 다소 과장됨
- PaperBench 20개 중 2개(10%) 역행 사례로 확인된 retrieval-precision 트레이드오프(무관한 스킬이 검색되어 오히려 방해)가 5,000개+ 규모 라이브러리에서 더 커질 가능성이 있으나 스케일링 분석 없음
- 스킬 생성 모델과 평가 대상 모델이 동일 계열(GPT-5.5/5.6-sol)이라 다른 백본(Claude, Gemini)에서도 동일 이득이 재현되는지는 검증되지 않음
