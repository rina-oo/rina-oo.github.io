# 음성 비서에 좌뇌와 우뇌를 달아주다 — VoiceMem: Streaming Dual-Brain Memory for Real-Time Interaction

> 원제: 음성 비서에 좌뇌와 우뇌를 달아주다 — VoiceMem: Streaming Dual-Brain Memory for Real-Time Interaction
> 리뷰: [블로그 전문](https://rina-oo.github.io/posts/2608.26005/)

## TL;DR
실시간 음성 대화 시스템(duplex SLM)을 위한 스트리밍 이중 뇌(dual-brain) 메모리 아키텍처. 정보를 다루는 좌뇌(스키마-엔티티 2단 그래프, Mem0 위에 얹는 경량 인덱스)와 감정·페르소나를 다루는 우뇌(독립 노드/교차-엔티티 노드, 단기·장기 정서 귀속)를 분리해 병렬로 관리하고, VAD가 기다리는 500ms 침묵 구간을 listening/speech tail·anticipation·searching 4단계로 쪼개 top-5 검색을 134ms 안에 끝낸다. 정보 기억 평균 76.39점(Mem0 대비 +24.12), 페르소나 기억 74.16점(MemOS 대비 +1.89), 자체 구축한 장기 음성 벤치마크 ChatMem-Bench 14개 중 11개 항목에서 1위. top-100이 아니라 top-5 예산에서도, 검색 이전에 후보 풀을 좁히면 정확도를 잃지 않는다는 게 핵심 주장.

## 핵심 기여
- 정보(좌뇌)와 감정·페르소나(우뇌)를 처음부터 다른 자료구조로 분리: 좌뇌는 관계(엣지) 중심 그래프, 우뇌는 개별 속성(description) 중심의 flat 구조.
- 좌뇌의 스키마-엔티티 인덱스가 검색 대상 풀을 미리 한 홉짜리 부분 그래프로 좁혀, top-5 예산에서도 밀도 높은 후보를 확보. 백엔드(Mem0) 자체는 그대로 두고 그 위에 얹는 방식이라 백엔드 교체가 가능(backend transfer 실험에서 Mem0/Zep/LangMem 모두 +15.8~29.5점 개선 확인).
- Cluster Emergence 메커니즘: 클러스터를 미리 정한 태그가 아니라 실제 쿼리 활성화 패턴의 query coherence(자카드 유사도 평균)로 판단해 스스로 갈라지게 함. LoCoMo처럼 세션이 긴 데이터셋에서 이득이 가장 큼(제거 시 -5.5점).
- 우뇌는 독립 노드(안정적 성향)와 교차-엔티티 노드(특정 대상에 대한 맥락적 감정)를 구분해, 일시적 반응이 성향으로 오인되거나 감정의 원인이 사라지는 문제를 구조적으로 방지. 단기(턴 단위)·장기(세션 단위) 귀속으로 갱신.
- 4단계 스트리밍 검색(listening → speech tail 0-200ms → anticipation 200-400ms → searching 400-500ms)으로 VAD 500ms 예산 안에 검색을 완전히 숨김. 실측 지연 134ms, K=3~100 구간에서 거의 변하지 않음(스키마 라우팅이 랭킹 전에 후보 풀을 이미 줄여놓기 때문).
- 블랙박스 온라인 증류(4단계: 메모리 세계 구성 → SLM 검증 온라인 증류 → 사람 큐레이션 → 검증)로 Qwen2.5/3-Omni, Step-Audio2-Mini를 메모리 인지형으로 미세조정. 이 과정에서 ChatMem-400K(학습)와 ChatMem-Bench(평가, 316문항·53시간·4차원·14카테고리) 확보.

## 한계
- 베이스라인들이 어떤 top-K로 평가됐는지 논문에 명시되지 않음. "10배 낮은 예산에서 이겼다"는 핵심 주장이 베이스라인 조건에 따라 설득력이 크게 달라지는데, 이 조건이 불투명함.
- ChatMem-Bench의 구체적 주석 프로토콜·품질 관리 방식이 "별도 후속 리포트"로 미뤄져 있어 현재로선 벤치마크 신뢰도를 독립적으로 검증할 수 없음.
- 모든 표가 "LLM-judge score"로만 표기되고 판사 모델·판사 간 일치도가 불명.
- 미세조정 응답 모델(VoiceMem‡)의 효과가 일관되지 않음. LoCoMo에서는 기본 모델을 능가하지만 LongMemEval Extr./Multi.와 Memora Rea.에서는 오히려 하락(예: Rea. 24.61 대 30.70). 어떤 조건에서 득이 되는지 분석 없음.
- 강조하는 134ms는 검색(retrieval)만의 지연이고, 비동기로 도는 갱신(add/update/delete/keep 판단, emergence LLM 판사 호출)의 LLM 호출 비용·시간은 정량화되지 않음. 실제 서비스 비용 추정에는 이 부분도 필요.
