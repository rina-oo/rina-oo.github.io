# EnvHarness: Awakening Static Worlds for Agent Learning

> 원제: EnvHarness: Awakening Static Worlds for Agent Learning
> 리뷰: [블로그 전문](https://rina-oo.github.io/posts/2608.19880/)

## TL;DR
환경을 처음부터 새로 만드는 대신 표준 인터페이스 위에 plug-in wrapper(Stage/Contract/Chain)를 씌워 에이전트의 약점을 겨냥해 재구성하는 EnvHarness와, 이를 자동화하는 진단 루프 EnvRigger를 제안한 논문. 다섯 개 벤치마크에서 원본 환경·도메인 특화 생성 파이프라인을 모두 앞서면서도, 검증기는 그대로 물려받는다는 게 핵심이다.

## 핵심 기여
- EnvHarness: 정적 환경을 코드 수정 없이 표준 reset/step 인터페이스에서만 감싸는 plug-in 계층. Stage(초기 상태를 행동 시퀀스 replay로 변형), Contract(행동/전이/관측 공간을 (f_A, f_T, f_O)로 재작성), Chain(두 환경을 검증기 AND로 이어 붙임) 세 컴포넌트로 구성되며, 원본 전이 함수 T와 검증기 R은 절대 건드리지 않아 신뢰성을 그대로 물려받음
- EnvRigger: 정책을 블랙박스로 취급해 Observe(baseline rollout 수집) → Diagnose(실패 원인 진단, 성공률이 너무 높으면 반대로 난이도 상향 진단) → Write(컴포넌트 코드 합성) → Validate(fresh rollout으로 accept/reject/refine 판정, 재시도 예산 5회) 루프를 도는 자동화 설계자
- 다섯 벤치마크(ALFWorld, WebArena, SWE-bench Verified, OfficeQA, SpreadsheetBench) 전체에서 원본 환경 스킬 대비 held-out +2.9~+9.0점, SWE-bench 평균 스텝 9.8% 감소. 도메인 특화 생성 베이스라인(GenEnv, VeriEnv, SWE-smith)도 전부 상회
- 환경 스케일링 실험에서 EnvHarness는 300개 환경까지 성능이 계속 상승하는 반면 원본/생성 환경은 100개 근처에서 정체 — 정책이 축적한 스킬을 반영해 다음 배치를 생성하는 co-evolution 구조가 원인으로 지목됨
- RL(GRPO, Qwen3-8B-base)에서도 유효: ALFWorld In-Dist +6.5점, WebShop score +3.6점. Cross-model(4개 백본, skill-free 성공률 30.7~67.2로 다양) 실험에서 이득 폭(2.7~3.7점)이 모델 강약과 거의 무관 — 진단 내용은 모델 능력에 따라 달라지지만 파이프라인 적용 가능성 자체는 유지됨

## 한계
- 설계 루프 비용: EnvRigger가 반복마다 환경을 굴려야 해서 약한 백본일수록 검증 통과까지 시간·추론 비용이 커짐 (환경 1개당 1회 지불이라는 점이 완화 요인)
- reset 가능한 gym 스타일 인터페이스를 전제 — Stage/Chain 모두 "환경을 되돌릴 수 있음"이 필요해 실제 서비스(이메일 발송, 주문)나 물리 로봇처럼 되돌릴 수 없는 환경에는 적용 불가
- Chain은 순수 순차 합성 + 검증기 AND만 지원해 서브태스크 간 의미적 관련성 판단이나 분기/공유 상태를 표현하지 못함
- (리뷰어 지적) designer와 policy가 동일 백본이라는 이유로 "distillation이 아니다"라고 방어하지만, Validate 단계 자체가 정책을 반복 rollout해 컴포넌트를 골라내는 구조라 일종의 self-distillation에 가까움 — 이 구분이 논문에 명확히 정리되어 있지 않음
- Validate 재시도 예산(5회)에 대한 민감도 ablation 부재, Contract가 생성하는 규칙이 프롬프트 힌트에 얼마나 의존하는지도 불명확
