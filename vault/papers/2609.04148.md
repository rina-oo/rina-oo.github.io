# Terminal-Universe: Turning Agent Trajectories into Scalable Terminal Environments

> 원제: Terminal-Universe: Turning Agent Trajectories into Scalable Terminal Environments
> 리뷰: [블로그 전문](https://rina-oo.github.io/posts/2609.04148/)

## TL;DR
trajectory와 environment를 같은 사건의 두 관점으로 보고, 코딩 에이전트 trajectory의 파일 읽기/쓰기/편집 기록을 역재생(replay)해 원래 실행 환경을 복원한 뒤 에이전트로 빈 부분을 보완(completion)한다. 복원된 워크스페이스에서 Intent Recovery/Single-WS/Cross-WS/Multi-Round 4가지 방식으로 새 태스크를 재합성해 37.3k개 검증 데이터를 만들고, Qwen3.5-27B SFT로 Terminal-Bench 2.1 +11.9p, EvoCode-Bench v2 MT@4 +13.8p를 달성. 환경을 새로 짓지 않고 이미 쌓인 trajectory 부산물에서 재활용 자원을 뽑아낸다는 프레이밍이 핵심.

## 핵심 기여
- 환경 복원 3단계: 결정론적 재생(파일 최초 상태 복구, 부분적 워크스페이스 $\widehat{E}_0$) → 에이전트 보완(빈 파일/의존성 채움, 완성 워크스페이스 $\widehat{E}$, 정답 유출 금지) → 충분성 필터(읽기전용 판정 에이전트가 이진 판정)
- Cross-WS: 워크스페이스 프로파일링 → TF-IDF 후보 검색 → LLM 판정으로 방향성 있는 기능 격차 탐지 → target(쓰기 가능)-reference(읽기 전용) 페어 태스크 생성. 서로 다른 두 프로젝트를 억지로 의존 관계로 엮어 실제 이식 시나리오 재현
- Multi-Round: 유저 에이전트가 요구사항 트래커 유지, 라운드마다 전용 검증기가 채점 후 결과를 자연어 피드백으로 변환해 전달(코딩 에이전트는 테스트/트레이스백 직접 못 봄). 라운드 성격(extension/revision/conflict)은 실제 결과에서 자연 발생, 목표 비율 없음
- 데이터 수율: 원본 trajectory 359,593개 중 81%가 재생 복잡도 부족으로 탈락, 오염 필터링/중복 제거 후 최종 태스크 충분 환경은 37,273개(약 10.4%)
- Ablation 핵심: 원본 trajectory 모방(36.7점) < 환경 복원 후 재풀이(52.1점); 재생만(48.7) < 재생+보완(52.9); 같은 예산이면 새 환경 추가(53.2→56.0)가 질문/정답 추가(53.8/53.9)보다 효과적

## 한계
- 논문이 인정: 표준 Ubuntu 24.04 컨테이너만 사용해 특수 의존성/빌드 케이스 재현도 저하 가능, 복원 환경의 도메인/언어 분포가 소스 trajectory 풀에 종속(Python 84.7%), 태스크 생성·풀이·검증을 교사 모델(Qwen3.7-Max) 하나가 전담해 그 모델의 한계가 데이터 품질 상한이 됨
- 리뷰어 지적: "deterministic replay"라는 이름과 달리 성능 향상의 대부분은 확률적인 Stage 2(에이전트 보완)에서 나옴 — 원본 환경 복원이라기보다 trajectory를 뼈대로 LLM이 새로 지어낸 것에 가까움. 완성 품질 검증이 30개 수작업 샘플(전체의 0.08%)뿐이라 정답 유출 없음 결론을 일반화하기엔 근거가 얇음. Cross-WS 카테고리별 결과에서 하락은 "런투런 노이즈"로, 상승은 "진짜 개선"으로 비대칭 해석. 코드/데이터셋 공개 여부 불명, 저장소 링크 없음
