# 토큰마다 모델을 갈아 끼우는 추론, 기존 서빙 엔진은 왜 못 버텼나 — TokenRouter (TokenRouter: Efficient Serving System for Token-Level LLM Routing)

> 원제: 토큰마다 모델을 갈아 끼우는 추론, 기존 서빙 엔진은 왜 못 버텼나 — TokenRouter (TokenRouter: Efficient Serving System for Token-Level LLM Routing)
> 리뷰: [블로그 전문](https://rina-oo.github.io/posts/2610.12242/)

## TL;DR
token-level routing(CITER, R2R, R-Stitch, Co-LLM, ME 등)은 토큰 단위로 작은/큰 모델을 오가며 효율과 품질을 동시에 잡는다고 알려져 있었지만, 공식 구현은 single-LLM 서빙 엔진(vLLM/SGLang) 가정 위에서 돌아가지 않아 R2R·Co-LLM은 오히려 LLM 단독 실행보다 느렸다. TokenRouter는 "request-centric programming, model-centric execution" 원칙으로 route-send-receive 세 함수 인터페이스를 제공하고, 모델별 서브서버가 비동기 3-루프로 실행되며 DTMC 기반 수학 모델로 유도한 delayed-batching threshold를 쓴다. 5개 알고리즘 × 3개 워크로드 전체에서 기존 구현 대비 2.01~64.15배 디코딩 처리량 향상을 보고한다.

## 핵심 기여
- route(결과 → 목적지 모델) / send(요청 → PeerReq) / receive(PeerReq → 로컬 요청) 세 함수만으로 서로 다른 신호(confidence, divergence, entropy, deferral, ensemble weight)를 쓰는 5개 라우팅 알고리즘을 표현하는 공통 인터페이스.
- client-server loop · decoding loop에 inter-model loop를 추가한 3-루프 비동기 실행 + running/finished 사이에 "pending" 상태를 둬서 handoff 시 prefix 매칭·KV 재할당을 생략하는 메커니즘. Std. Serving 베이스라인 분석에서 이 재매칭 오버헤드가 SLM 스텝 시간의 약 85%를 차지함을 실측으로 보임.
- batch admission delay를 줄이기 위한 delayed-batching 스케줄러. 시스템을 DTMC로 모델링해 정상상태 처리량 $T(\mathbf{B}) = \mathbb{E}[g(\mathbf{s},\mathbf{M})]/\mathbb{E}[\tau(\mathbf{s})]$을 유도하고 이를 최대화하는 threshold $\mathbf{B}^\star$를 analytically 탐색.
- 엔지니어링 최적화(extend-mode CUDA 그래프, in-process router, joint KV 할당)와 시스템 설계(비동기 실행+delayed batching)의 기여를 분리한 ablation: 동시성 8에서 전자가 1.71배, 후자가 추가 1.61배로 총 2.76배.
- 공식 구현 대비 최대 21.97배(처리량) / 21.61배(지연시간) 개선, 모델 쌍 4종 교체에도 1.99~3.21배 유지되는 일반화 확인.

## 한계
- 평가 대상 5개 알고리즘이 모두 "작은 모델 기본, 큰 모델에 가끔 도움 요청"하는 2~3개 모델 비대칭 구조. 분포 융합형(quality-oriented) 라우팅은 평가에 없어 인터페이스의 일반성이 완전히 검증되지는 않음.
- DTMC 모델이 연속 디코딩 스텝 수의 geometric 분포를 가정하며, 저자도 이 가정이 깨지는 corner case를 future work로 남김 — 어떤 라우팅 정책이 가정을 깨는지는 명시 안 됨.
- 기본 실험 설정은 CUDA MPS로 GPU를 overlap해서 쓰는데, 부록에서 non-overlapping이 평균 6.43% 더 빠르다고 보고하면서도 overlap을 기본값으로 쓴 이유 설명은 짧음.
- GitHub(`thu-nics/TokenRouter`)는 placeholder가 아니라 실제 코드(route/send/receive 사용법 포함)가 올라와 있으나, 공개 초기 단계라 논문의 모든 ablation 설정이 바로 재현 가능한지는 저장소만으로 확신하기 어려움.
